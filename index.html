Executive Summary · Salesforce CRM Security Hardening · v1.0.0 · last modified 2026-05-04

Most Salesforce breaches aren't platform breaches.

They are customer-side configuration, integration, and human-factor breaches — vishing, OAuth abuse, misconfigured Experience Cloud guest profiles, and rogue browser extensions. The frontier-AI threat (Anthropic's Claude Mythos) is real but contained; the actual attack surface in 2024–2026 looks a lot like the attack surface of 2019, just faster and louder. Bottom Line Up Front

In the 2024–2026 corpus, the recurring control surface is the customer-managed layer of the Salesforce shared-responsibility model: how identity is gated, how Experience Cloud guest profiles are scoped, how Connected Apps and OAuth grants are governed, how integration secrets and certificates are rotated, how Apex and Flow run-context is constrained, and how detection is wired to response. The platform side is hardened by Salesforce; the configuration / integration / human side is the customer's working surface within the partnership. Platform features still require correct use, and safe defaults reduce but don't eliminate the work that comes with that.

What changed with Mythos. Anthropic's frontier model is restricted to Project Glasswing. The unauthorized-access incident reported in April 2026 was a third-party-vendor supply-chain story, not a direct compromise of Anthropic. Salesforce Ben[1] captured the pattern: the attack surface now extends through every Connected App, every OAuth grant, every AI tool an employee authorizes. Vishing, not frontier AI, is the real Mythos.

90-Minute Hardening Sprint — If You Can Only Do One Thing This Quarter

For orgs with no security budget and no dedicated time, the absolute minimum-viable hardening pass. Every action below is free (no Shield, no SSPM, no add-on), and the entire list fits inside 90 minutes for a single admin in a single sitting. Each captures meaningful risk reduction against the 2024–2026 corpus.

  1. 5 min — Setup → OAuth and OpenID Connect Settings → turn on "Block authentication for uninstalled connected apps." Closes the UNC6040 vishing pivot.
  2. 5 min — Same screen → block User-Agent and Username-Password OAuth flows. Removes deprecated/unsafe flows org-wide.
  3. 10 min — Setup → Health Check → record the baseline score; fix every High-Risk item inline. Captures whatever the platform's own scoring identifies.
  4. 15 min — Setup → Connected Apps OAuth Usage → export the report; revoke any app you cannot identify a business owner for. Closes ISV-token-theft persistence (UNC6395 / Drift pattern).
  5. 10 min — Setup → Identity Verification → require a Security Key as the verification method for every admin profile. FIDO2 is the only MFA factor that survives vishing.
  6. 10 min — Setup → Session Settings → set Timeout to 2 hours; turn on Lock sessions to IP; require HTTPS-only. Limits stolen-session blast radius.
  7. 10 min — Run two SOQL queries: Modify All Data holders and View All Data holders. Manually compare against your expected admin list. Schedule any unexpected holder for revocation. Right-sizes the largest blast-radius grants.
  8. 10 min — Audit each Experience Cloud guest profile: turn off API Enabled, View All Users, Run Reports, Export Reports, Manage Public Documents (if any are on). Closes the Krebs / DIVD-2026-00005 pattern.
  9. 5 min — Subscribe your team to Salesforce Security Advisories at security.salesforce.com. Free signal channel for new advisories.
  10. 10 min — Save the Health Check export, OAuth Usage CSV, and the MAD/VAD lists to a secure, retention-stamped location. Establishes your audit-pack baseline for this quarter.

The Mythos Question — What's Real, What's Hype

What Mythos is. Anthropic's most capable model, restricted to the Project Glasswing[2] research program. Public reporting describes strong vulnerability-finding performance during restricted research testing; reported government and banking-sector consultations took place in April 2026. Treat these as early public reporting, not operational evidence about Salesforce orgs.

What happened. Bloomberg reported[3] that unauthorized users gained access via a third-party vendor environment. Anthropic's official statement: no evidence the access went beyond the vendor environment; no Anthropic systems impacted.

What it changes for Salesforce customers. Per Salesforce's official response[4]: "an acceleration of work already underway." The supply-chain framing matters more than the frontier-capability framing. Your agentic attack surface now extends through every Connected App, every OAuth grant, every AI tool your employees authorize — and that was true before Mythos.

What still moves the needle. Vishing (UNC6040), OAuth abuse via compromised ISVs (UNC6395 / Salesloft Drift, 700+ orgs), Experience Cloud guest profile misconfig (Krebs 2023 → ongoing), browser extensions hijacking authenticated sessions (35+ extensions, 2.6M users in Dec 2024[5]), AI prompt injection via web-to-lead and case intake forms[6].

Bottom Line Up Front (Technical)

The shared-responsibility model for Salesforce is unambiguous: Salesforce hardens the platform; the customer hardens the configuration, the integration, the code, the data, the people, and the partner ecosystem. This document covers the customer half. It does not duplicate Salesforce's own security posture (covered at trust.salesforce.com[10]); it covers everything else.

The 2024–2026 threat corpus — UNC6040 (vishing → Data Loader OAuth grant), UNC6395 (Salesloft Drift OAuth tokens, 700+ orgs[11]), Krebs-pattern Experience Cloud guest exposure (Vermont, TCF Bank[12]; ongoing GraphQL exposure DIVD-2026-00005[13]), 35+ malicious browser extensions (December 2024 supply chain[14]), AI prompt injection via web-to-lead and case intake forms (WithSecure 2026[15]), and the April 2026 Mythos third-party-vendor incident (Bloomberg[3]) — all collapse into a single architectural pattern: the customer's customer-managed control surface is where the leverage sits. Mythos accelerates the timeline; it does not change the surface.

Ten pillars, ordered by dependency: Identity gates Access; Access gates Experience Cloud; Experience Cloud and Connected Apps are the highest-leverage exposures; mTLS gates external integrations; secure code constrains run-context; data classification precedes encryption precedes detection precedes response; DevSecOps closes the supply chain; Defensive AI overlays the entire stack.

Three time horizons: ≤30-day quick wins (Health Check, MFA, Block Uninstalled Apps, OAuth audit), 30–90-day high-risk mitigation (Experience Cloud audit, View All / Modify All strip, cert rotation prep, Real-Time EM + SIEM, Transaction Security policies), and 90-day–12-month structural refactor (data classification, Profile → Permission Set Group migration, Shield rollout, DevSecOps pipeline, backup & recovery). Budget approximately 30% regression-testing overhead on every change — this is an author estimate based on field experience, not a vendor-cited number; your mileage will vary by integration density.

Threat Brief — 2024–2026 Salesforce Attack Landscape

A note before the catalog. Every incident in this brief touched real people. Employees who answered phones in good faith and took the blame for trusting an attacker. Residents whose unemployment-assistance applications surfaced their SSNs to the public internet. Bank customers whose account details left their bank's control. Admins, architects, and security teams who walked into Monday morning with a breach notification and an investigation. Partners and ISVs who learned about a customer impact at the same time their customer did. The point of this document is to reduce the next set of those events — not to score points about whose configuration was at fault. Treat the catalog below in that spirit.

Six attack categories account for nearly all observed customer-side compromise in the corpus. Ranked by incident scale and reuse:

  1. Vishing → OAuth grant abuse (UNC6040 / ShinyHunters). Attackers impersonate IT support over voice, talk the user through visiting Salesforce's verification page, capture the verification code, and ride a freshly-issued OAuth access token into the user's Data Loader. Confirmed targets in primary reporting include Google, Cisco, Adidas, Qantas, Allianz Life, and LVMH-group brands (Louis Vuitton, Dior, Tiffany & Co.)[16][17]; additional names appearing in secondary coverage include Pandora, Chanel, and Starbucks Singapore (treat as not yet primary-source-confirmed). Per Google Threat Intelligence[17], the campaign was a coordinated extortion operation.
  2. ISV / Connected App supply-chain compromise (UNC6395 / Salesloft Drift). Attackers compromised Salesloft GitHub repositories March–June 2025, then used the access to harvest OAuth tokens for the Drift integration to 700+ Salesforce customer environments, including Cloudflare, Zscaler, and Palo Alto Networks[18]. Drift was pulled from AppExchange; tokens were revoked in August 2025. The pattern: passing AppExchange Security Review is necessary but not sufficient.
  3. Experience Cloud / Communities guest-user record exposure (Krebs pattern). Public Salesforce Community sites with misconfigured guest profiles exposing private records — full names, SSNs, addresses, bank account numbers — affecting residents and customers whose data crossed the trust boundary unintentionally. Confirmed at the State of Vermont (multiple sites, including a Pandemic Unemployment Assistance program where applicants' SSNs and bank-account numbers were directly accessible), TCF Bank (Huntington), and hundreds of other organizations identified by independent researcher Charan Akiri[12]. The 2026 reprise: DIVD-2026-00005[13], a GraphQL-endpoint variant identified by AppOmni research.
  4. Browser-extension session hijack. 33 Chrome extensions (Cyberhaven primary reporting; some industry coverage cited higher counts) compromised in a December 2024 supply-chain attack, stealing session cookies and credentials from 2.6 million users (per Cyberhaven primary reporting)[14]. Extensions are invisible to Salesforce's OAuth Usage and Connected App reports because they piggyback on the authenticated browser session rather than requesting their own OAuth grant. Endpoint allowlisting (Chrome Enterprise) is the only defense.
  5. AI prompt injection via web forms and case intake. WithSecure 2026[15] documents prompt injection delivered via Web-to-Lead, Web-to-Case, and Email-to-Case intake reaching Salesforce-side AI agents. Adjacent: malicious file uploads (Word docs >2/3 of detections; image files >25%, mostly QR-code "quishing"), 83% of detections concentrated in a single category.
  6. Frontier-AI third-party-vendor compromise (Mythos). April 2026 Bloomberg report: unauthorized access to Anthropic's Mythos Preview[2] via a third-party vendor environment. Anthropic's official statement: no Anthropic systems impacted. Per Salesforce Ben[1]: "the Mythos access story is a supply-chain story." Salesforce's official response[4]: "an acceleration of work already underway." Worth acknowledging here: Project Glasswing itself is a proactive Anthropic safety measure — the restriction is the safeguard, and its existence narrowed the blast radius of this incident.

1.2 · FIDO2 / WebAuthn for Salesforce

Salesforce supports WebAuthn / FIDO2 security keys[21] as a verification method. Configuration is per-user; enrollment is via Identity Verification settings.

Relying-party configuration choices

  • authenticatorAttachment: cross-platform (hardware keys only) for high-assurance operators; platform (Touch ID / Windows Hello) for end-users on managed devices. Mixing them per-population is the right call.
  • userVerification: discouraged (touch-only) for high-frequency operator use; required (touch + PIN/biometric on the key) for emergency-tier actions.
  • residentKey / discoverable credentials: preferred for end-user passkey use cases; not required for operator-only deployments.

The recovery-code problem (and the pattern that solves it)

Hardware keys break. Operators travel without them. The recovery path must not weaken the FIDO2 assurance. The pattern: two-layer recovery — (1) per-user recovery codes (8 single-use codes generated at enrollment, 60-bit entropy, SHA-256 hashed with per-code salt, displayed once) usable in place of a single touch; (2) when codes are exhausted, time-delayed self-recovery — first OTP to email starts a 72-hour hold during which alerts go to all admins; second OTP after 72 hours unlocks re-enrollment of a new key. A co-admin with their own hardware key can expedite the hold to 24 hours. Solo admin: 72 hours, no shortcut. The time delay is the security mechanism — it survives email compromise.

Recovery codes consume the same downstream gate as a hardware-key touch (a one-time X-Operator-Fido2-Token with 60-second TTL, single-use, server-issued). They do not short-circuit the FIDO2 enforcement layer; they substitute for the touch only.

1.3 · High Assurance Sessions & Step-Up

Standard vs. High Assurance is like a venue wristband vs. a backstage pass. The wristband gets you in the building; the backstage pass is checked again at the door of the green room. Sensitive Salesforce actions are the green room.
  • Salesforce Help — Session security
  • Salesforce Help — High Assurance sessions
  • Wikipedia — Step-up authentication

A Salesforce session has a session security level: Standard or High Assurance. The level is set by the factor used to authenticate. Per-operation, you can require High Assurance via Session Settings → Session Security Levels. Standard-level sessions hitting a High-Assurance gate are challenged for a stronger factor before the operation proceeds.

Where to enforce High Assurance

  • Mass-export reports and list views (the UNC6040 exfil path)
  • Bulk API and Data Loader sessions
  • Connected App authorization (admin pre-approval flow)
  • Modify All Data / View All Data scope grants
  • Setup — Auth, Permission, Domain, Cert, Connected App pages
  • Custom Apex pages handling PII access or decryption

The implementation hook is one of three

  1. Session Security Levels on Connected App OAuth Policies — declarative
  2. Custom Login Flow with a Visualforce or Flow Builder page that calls Auth.SessionManagement.setSessionLevel(Auth.SessionLevel.HIGH_ASSURANCE) after re-challenge — declarative + a small Apex helper
  3. Transaction Security policy with Action Multi-Factor Authentication — rule-based, runs at event time

Pillar 8 covers the Transaction Security route in detail; this card establishes the contract. Pillar 1.4 covers Custom Login Flows as the universal hook.

1.4 · Custom Login Flows as a Universal Hook

A Custom Login Flow[22] runs after Salesforce authenticates the user but before the user reaches the homepage. It is the most general step-up hook in the platform. Two implementation styles: Flow Builder (recommended) or Visualforce (legacy). Flows are connected to profiles via Setup → Login Flows.

What you can do in a login flow

  • Force a fresh MFA challenge for sensitive sessions, even if the SSO assertion satisfied MFA
  • Read context attributes (IP, browser, time, day) and conditionally branch
  • Display a banner / disclosure / acceptable-use notice requiring acknowledgment
  • Limit concurrent sessions per user (terminate older sessions)
  • Restrict simultaneous device count by querying the User Sessions object
  • Run an Apex prerun check (e.g., is the user's hardware key still attested? has their domain ACL been revoked?) and route to a remediation page on fail
  • Log-out users on policy violation via Auth.SessionManagement.finishLoginFlow() with a logout flag

The pattern: one Login Flow per profile-tier, doing only the lightest checks in the base path; deferring privileged-operation step-up to Transaction Security policies that fire at event time. Login Flows are not free — they add latency to every login. Use them for what only they can do.

1.5 · SAML / OIDC SSO Architecture

Salesforce supports both SAML 2.0 and OpenID Connect (OIDC) for SSO. Both can be used with Salesforce as a Service Provider (most common) or as an Identity Provider (Salesforce-as-IdP for downstream apps).

SAML SP-initiated SSO — the canonical pattern

  • My Domain is required — the SP entityID is the My Domain URL
  • Single Sign-On Settings in Setup configures the trust relationship: IdP entityID, IdP login URL, identity provider certificate (for assertion signature validation), Identity Type (Username vs. Federation ID; Federation ID is the recommended choice for resilience to email changes)
  • SAML SSO Use Cases: SP-initiated (recommended), IdP-initiated (acceptable; less resilient to deep links)
  • Just-in-Time (JIT) Provisioning: when the assertion arrives for an unknown user, create the user record from the assertion attributes. Apex JIT handler (Auth.SamlJitHandler) is the extension point for non-trivial mappings (e.g., IdP group → Permission Set Group)

OIDC equivalents

  • Authentication Provider in Setup — references an OIDC IdP
  • Authentication Method References (amr) — pulled from the OIDC token JSON, used to gate operations (e.g., require amr=hwk for High Assurance)
  • OIDC custom claims — pass IdP groups, device attestation, deviceId, geographic region for downstream Apex consumption

Custom claims for fine-grained authorization

The single most underused power lever: custom claims in the SAML assertion or OIDC token, consumed by an Apex registration handler, mapped to Salesforce-side authorization primitives (Permission Set Groups, custom permissions, federated identifier). This is how you enforce things like "only users in the IdP's FinSec group get the Treasury_Operator Permission Set Group on every login — no manual provisioning, no drift."

1.6 · Custom Auth Providers + Apex Handlers (the Power Lever)

Out-of-the-box SAML and OIDC carry standard claims. Real-world security postures need more: device attestation results, IdP-side risk scores, group memberships, geographic constraints, just-in-time access grants. This is what Custom Auth Providers and Apex registration / SAML JIT handlers exist for.

Three extension points (use them deliberately)

ExtensionInterfaceWhat it lets you do
Custom Auth Provider Auth.AuthProviderPlugin Implement an entirely non-standard auth protocol (e.g., a partner's bespoke attestation, a hardware-bound key exchange) and surface it as a Salesforce Auth Provider. The platform handles routing; you handle the protocol.
Apex Registration Handler (OIDC / OAuth) Auth.RegistrationHandler On every successful auth, decide what user record to create or update. Read OIDC custom claims; map IdP groups to PermSet Groups; assign Federation ID; deny user creation if the assertion lacks a required claim.
Apex SAML JIT Handler Auth.SamlJitHandler SAML equivalent of the Registration Handler. Read SAML attribute statements, including custom attributes; create/update user; assign profile and PermSet Groups; reject the assertion entirely (returning null) on policy violation.

Patterns worth implementing

  • Group-driven entitlement. IdP returns a groups claim. Handler hashes the groups, looks them up in a custom-metadata mapping table (IdP_Group_Permission_Mapping__mdt), grants and revokes Permission Set Groups on every login. Result: zero permission drift; admin changes happen in the IdP, not in Salesforce.
  • Device-bound JIT. IdP returns a deviceId + attestation claim. Handler stores the deviceId on a custom field on User, denies login if attestation is "untrusted".
  • Geographic constraint. IdP returns a geo claim. Handler denies login from outside the user's allowed regions. (Note: Trusted IP Ranges are coarser; this is per-user.)
  • Step-up trigger. Handler sets a flag on the User record indicating that the next sensitive operation should challenge for High Assurance; Transaction Security reads it.
  • Audit on auth. Handler writes a SecAuth__c record with full assertion metadata (hashed where appropriate) for forensic queries.

What not to do. Putting business logic in handlers that requires SOQL on every login. Handler latency adds to every login. Cache custom-metadata lookups; do not query large objects.

1.7 · My Domain, Identity Verification, Device Activation

Three platform-level controls that are baseline (not optional) in 2026:

My Domain

  • Required for SSO, Lightning Experience, Mobile Publisher, and many security features
  • Provides a stable, branded login URL (e.g., acme.my.salesforce.com)
  • Login URLs visible in Login History — phishing detection signal
  • Hardening: enable "Prevent login from https://login.salesforce.com" once My Domain is fully cut over

Identity Verification

  • Challenges the user to verify identity when logging in from a new browser, new device, or IP outside trusted range
  • Configured under Identity Verification settings; methods include email code, SMS, TOTP, security key
  • Hardening: require security key as the verification method for admin profiles

Device Activation

  • Required for SSO logins as of February 2026 per Vantage Point[20]
  • Confirms the device is authorized, distinct from the SSO assertion's user identity
  • The chain: SSO authenticates the user; Device Activation authenticates the device; together they make session hijacking by token theft far harder

Together, My Domain + Identity Verification + Device Activation establish that both a known user and a known device must be present. Vishing can compromise the user; it cannot compromise the device.

1.8 · Tier-Based Privilege Gating — Stock vs. Bespoke

The instinct from operator-security practice is to classify every privileged action into tiers and gate each with a factor combination — typed confirmation phrases, layered FIDO2 + TOTP, custom session tokens. That model assumes a runtime where you control the entire stack. Salesforce CRM is not that runtime. The honest engineering question is therefore which tier behaviors are actually achievable with stock platform primitives, and which require bespoke custom build that re-implements the platform. This card draws that line.

Threat-model reality check — the API surface dominates

Before designing any UI confirmation step, name the threat model. The 2024–2026 corpus is overwhelmingly API and token-based, not UI:

  • UNC6040 — vishing convinces a user to approve a Connected App; the data leaves via Bulk API in the attacker's Data Loader.
  • UNC6395 / Salesloft Drift — refresh tokens stolen from an ISV's repo; attacker hits REST/Bulk directly, no UI ever involved.
  • Browser-extension session hijack — the sid cookie is reused, but exfiltration runs through API calls the extension issues.
  • Krebs-pattern guest exposure — the surface is public Aura/LWC controllers queried via API.

Implication: UI-side confirmation prompts catch a small slice of the model. The dominant gate is API-side. Re-implementing OOTB Lightning to inject typed-confirmation steps is a poor use of engineering budget unless the work is bounded to a handful of high-stakes record types.

2 · Access Control & Least-Privilege Migration

Least-privilege access (only what each role needs, nothing more) is the foundation of every later pillar. Salesforce is moving from the legacy profile-based access model to a modern permission-set model; the original Spring '26 enforcement date was postponed[42], but the direction is unambiguous. The full migration is a roughly 12-month project, but a 90-day "high-risk mitigation" sub-track — stripping the broadest privileges from anyone who doesn't truly need them — captures most of the value upfront.

2.1 · Organization-Wide Defaults — Private as the Foundation

OWD sets the maximum default access a user has to records they do not own. Every other sharing layer can only widen that default (or, with Restriction Rules, narrow it for specific queries). Set OWD to Private for every standard and custom object that holds sensitive data, and use sharing layers to grant exceptions deliberately.

External vs. internal OWD (separate settings)

  • External Org-Wide Defaults are automatically enabled for orgs created Spring '20 or after, and for any org with Salesforce Experiences or portals enabled[23]
  • External users can have a different (more restrictive) default than internal users on the same object
  • Guest users have OWD set to Private for all objects, and this is not configurable — their access is widened only by guest user sharing rules (covered in 2.4)

Common mistakes

  • Public Read/Write on Account or Opportunity for "convenience" — this defeats the entire access model and is the primary cause of audit findings
  • Mixing Public Read-Only with criteria-based sharing rules that grant Read/Write to "All Internal Users" — effectively Public Read/Write with extra steps
  • Setting external OWD to Public on objects accessible from Experience Cloud — this is the Krebs-pattern data-bleed root cause[12]

2.2 · Profile → Permission Set Group Migration (timeline in flux)

Salesforce has stated that profile-based permissions are being retired as the primary permission grant mechanism. The original Spring '26 enforcement date was postponed (per Salesforce Help[42]); a revised hard date is pending as of this snapshot. The architectural direction, however, is unambiguous: Permission Set Groups (PSGs) are the modern primitive — a named bundle of Permission Sets, assignable to users, composable, and unlike profiles, multiple per user. Start migrating now — the deferred deadline buys time for proper sequencing, not for delay.

Realistic timing

  • 12-month structural refactor: full Profile → PSG model migration, integration test harness, deprecate legacy profile permissions
  • 90-day high-risk mitigation sub-track: strip View All / Modify All from non-System-Admin profiles, audit Permission Set assignments quarterly — captures most of the risk reduction up-front
  • ~30% regression-testing overhead on every PSG cutover sprint (author estimate; not vendor-cited) — flows, Apex tests, integrations, reports break in non-obvious ways when permission topology changes

Migration shape (in-context example: profile diff → PSG composition)

The conceptual transform: a Sales-Manager profile becomes "Base Sales user" + "Manager scope" + "Quote-create permission" — three composable Permission Sets bundled in a PSG.

  • Calculated PSGs — the platform recalculates the effective permissions whenever the membership changes, with a status indicator (Updated / Outdated / Failed)
  • Auditability — PSG assignment is observable in PermissionSetAssignment objects, queryable, reportable, attestable

2.3 · Role Hierarchy — Visibility, Not Permission

The role hierarchy controls visibility of records owned by users below in the hierarchy. It does not grant create / edit / delete permissions — those come from Permission Set Groups. Confusing the two is one of the most common architectural errors.

  • Users higher in the hierarchy automatically see records owned by or shared with users below them
  • This automatic visibility can be disabled on a per-object basis ("Grant Access Using Hierarchies" checkbox) — commonly disabled on objects holding HR / compensation / executive data
  • Territory hierarchy works alongside the role hierarchy for sales-territory-based visibility
  • The hierarchy is for visibility; profile or PSG determines what the user can do with the records they can see

Pattern. Keep the role hierarchy shallow. Each level adds visibility surface and audit complexity. If your hierarchy mirrors a 7-level organizational chart, you have a 7-level audit problem. Most orgs work cleanly at 3–5 levels with sharing rules filling the gaps.

2.4 · Sharing Rules — Ownership, Criteria, and the Guest Red Flag

Sharing rules widen access beyond OWD. They come in flavors:

  • Owner-based sharing — share records owned by a group/role to another group/role
  • Criteria-based sharing — share records matching a filter to a group/role
  • Guest user sharing rules — share records to the unauthenticated guest user profile of an Experience Cloud site (RED FLAG; covered in detail in Pillar 3)
  • Manual sharing — one-off grants by record owner; visible in the Sharing button on the record
  • Implicit sharing — platform-driven sharing for parent/child relationships (Account-Team, Opportunity-Team, Account-Contact)
  • Apex Managed Sharing — programmatic __Share rows inserted by Apex

Limits. Up to 300 sharing rules per object, including up to 50 criteria-based or guest user sharing rules[24]. Hitting these limits is a strong signal that the sharing model needs simplification or restructuring.

Guest user sharing rules — the red flag

Every guest user sharing rule is, by definition, granting access to unauthenticated users. Every one needs an explicit business justification, a signed-off review, and an entry in the quarterly attestation pack. Most data exposure incidents on Salesforce platform in 2023–2026 trace back to a guest user sharing rule that should not have existed.

2.5 · Restriction Rules — The Narrow-Access Primitive

A relatively recent platform feature: Restriction Rules let you narrow the records a user can see, even if Sharing Rules and OWD would otherwise grant access. Where Sharing Rules can only widen, Restriction Rules narrow.

Where Restriction Rules excel

  • Compliance fences. "Sales reps in EU may not see Records flagged as US-only, even if the Sharing model would otherwise grant access."
  • Data classification quarantines. "Records classified as 'Restricted' are visible only to users in the Restricted_Data_Custodian PSG."
  • Sub-tenant isolation. Multi-brand orgs where Brand A reps must never see Brand B records, even on shared objects.

Mechanics

  • Defined per object; targets a subset of users (by group, role, or individual)
  • Includes a record filter expression evaluated at query time
  • Records that fail the filter are removed from query results — not raise an error, simply absent
  • Apply to most query surfaces (SOQL, SOSL, reports, list views)

Pattern. Use Restriction Rules for compliance fences that must hold even when admin error widens sharing accidentally. They are the belt-and-suspenders for the sharing model.

2.6 · Field-Level Security and the Apex Run-Mode Contract

Object permissions decide which file cabinets you can open. Field-Level Security decides which lines on each form inside the cabinet you can read. The UI hides the lines you shouldn't see automatically — but Apex code, by default, ignores them. That is the trap.

  • Apex docs — with/without sharing

Object-level permissions tell you whether a user can read a row; Field-Level Security (FLS) tells you whether they can read any individual field on that row. FLS is enforced across UI surfaces automatically (detail pages, related lists, list views, reports, search, email merge). It is not automatically enforced in Apex.

Sharing keyword contract

  • with sharing — class respects the running user's record sharing
  • without sharing — class ignores sharing; use only with explicit business justification and only for narrow operations
  • inherited sharing — recommended default for utility classes; inherits the calling context's sharing
  • Default (no keyword) — behaves as with sharing in some contexts and without sharing in others; never rely on the default

Pattern. New Apex code uses WITH USER_MODE and AccessLevel.USER_MODE universally. Legacy code is migrated incrementally, prioritizing classes that touch sensitive objects or are reachable from guest user contexts.

2.7 · Reports, List Views, Exports — The Exfiltration Surface

The most common Salesforce exfiltration vector is not a hack. It is a privileged user clicking Export on a report. The 2025 vishing wave (UNC6040) used a fresh OAuth token against Data Loader for exactly this reason — Data Loader is just a high-throughput export UI[16].

The export-permission stack

  • Export Reports — user permission gating CSV/XLSX export of any report
  • API Enabled — user permission gating API access; without it, no Bulk API or Data Loader
  • Bulk API / Data Loader — high-throughput record export; tied to API Enabled
  • Run Reports / Manage Public Reports — granular report rights
  • CRM Analytics export — separate permission for CRM Analytics dashboard data export
  • Scheduled Reports — reports emailed on a cadence; the recipient list is the exfil channel

Hardening levers

  • Per-PSG export gates. Export Reports and API Enabled live in dedicated Permission Sets; granted by PSG composition, not profile baseline. Quarterly attestation per assignee.
  • Transaction Security on report export: Block / require MFA / Notify on report exports above a row threshold (e.g., 10K rows), or off-hours, or from non-trusted IP. Pillar 8 has the policy patterns; Appendix E has the Apex.
  • Scheduled Report recipient governance. Quarterly review — recipients on scheduled-report email distribution lists are de-facto authorized data exporters.
  • Data Loader login alert. Login History → Application = "Data Loader Bulk" or "Salesforce Data Loader" should be alerted on for any non-integration user.

2.8 · Files / ContentDocument — The Silent Leak Path

Files (Salesforce Files / ContentDocument / ContentVersion) have their own sharing model, parallel to record sharing. A file shared "with all internal users" is shared with every license that has Chatter Free or above. A file shared via "public link" is accessible to anyone with the URL (and no expiration unless set).

Where files leak

  • Public links. Generated by users with Create Public Links; URLs do not require Salesforce login. Hardening: disable the user permission for non-trusted profiles, require password on public links, set short expiration windows, audit existing public links.
  • "Anyone in your company" sharing. A file uploaded to a Chatter Group or attached to a record can be set to "Anyone in your company" — which includes external users on Chatter Free / Chatter External licenses.
  • Library files. Salesforce Files Library admins can over-grant; libraries are rarely audited.
  • Email attachments. Files attached via Email-to-Case land in ContentDocument with inherited sharing — review the inheritance.

Hardening levers

  • Disable Create Public Links from the standard user permission set; grant only to trusted profiles via PSG
  • Require password and set max-30-day expiration on public links via Files Connect or org-wide setting
  • Quarterly audit of ContentDistribution records (the public link backing object) — SOQL: SELECT Id, Name, ExpiryDate, PreferencesPasswordRequired FROM ContentDistribution WHERE PreferencesAllowPDFDownload = true
  • Apex code that creates ContentDocumentLink rows must use USER_MODE; "share with all internal users" should be a deliberate, reviewed pattern, not a default

2.9 · Modify All Data / View All Data — Quarterly Attestation

These two user permissions are the largest blast-radius grants in the platform. Their default holders are System Administrator profile users. Every additional holder is an audit finding.

Quarterly attestation pack (the default cadence)

  • SOQL: SELECT Assignee.Username FROM PermissionSetAssignment WHERE PermissionSet.PermissionsViewAllData = true — full list of View All Data holders
  • Same query for PermissionsModifyAllData
  • Same for PermissionsViewSetup and PermissionsManageUsers
  • Cross-reference against the prior quarter's attestation; flag any added grant for justification
  • Sign-off: dated, signed (electronically), retained for the regulatory window

The "strip ahead of migration" pattern

The 90-day high-risk mitigation lane (2.2) does this attestation once, intensively, and removes every grant that lacks a documented justification. This is the single highest-leverage one-time hardening action in the access control pillar — it rate-limits the consequences of every other breach in the corpus.

3.1 · The Persistent Data-Bleed Mechanism (Anatomy)

The bleed has a structure. Every published incident decomposes into the same five-step exploit chain:

  1. Discovery. An attacker (or researcher) finds a public Experience Cloud URL via Google dorks (e.g., inurl:site.com, inurl:my.salesforce-experience.com), AppExchange enumeration, or direct browsing.
  2. Surface enumeration. The attacker enumerates Aura controllers, LWC endpoints, GraphQL queries, or REST endpoints reachable as the guest user. This is mostly automated — tools like SOQL injection probes, GraphQL introspection, and Aura action enumeration are public.
  3. Permission probe. The attacker runs queries against standard objects (Account, Contact, Case) and custom objects to discover which are accessible. The error vs. data response discloses the permission state.
  4. Sharing pivot. Where one guest sharing rule grants Read on Account, and "Grant Access Using Hierarchies" is enabled with Account-Contact implicit sharing, Contact records automatically become readable. One misconfigured rule unlocks adjacent objects via implicit sharing.
  5. Bulk extraction. SOQL with LIMIT 50000 via the Aura action returns pages of records. No alarms. No login. No anomaly to detect, because to Salesforce, this is a correctly-authorized guest user doing exactly what the configuration permits.

The breach signal is not in the access logs — the access is by design. The breach signal is in the configuration drift between the intended exposure and the actual exposure. That is the audit's job.

3.4 · Guest User Sharing Rules — Per-Rule Review

Every guest user sharing rule is an unauthenticated access grant. Treat it as such. The audit pattern is per-rule, with documented business justification, on a quarterly cadence.

Per-rule review template

  • Rule name and object. What is being shared.
  • Filter / criteria. Which records (be specific; "all open Cases" is rarely the intended scope — "Cases where IsPublished__c = true and Status = 'Published Help Article'" almost certainly is).
  • Access level. Read or Read/Write. Read/Write to a guest user is rarely correct.
  • Business justification. Why does the unauthenticated public need this access? Whose decision was it? When was it last reviewed?
  • Coverage check. Does the criteria filter actually cover the intended records, and only those? Run the query as the guest user (in a sandbox) and inspect the result set.
  • Implicit-sharing pivot check. If this object has implicit-sharing relationships (Account-Contact, Account-Opportunity, etc.), what becomes accessible because of this rule?
  • Sign-off. Dated, signed (electronic), retained.

Common failure modes

  • Filter drift. A rule with filter IsPublic__c = true works until someone adds a custom field IsPublic__c to a related object and forgets to scope it — then every record where any related object's IsPublic__c = true becomes accessible.
  • "All" filters. A rule that shares "All records owned by group X" is shared until group membership changes — new internal users added to X auto-publish their records.
  • Hierarchy-based grant to guests. Hierarchical sharing was disabled for guest users in Winter '21, but legacy rules sometimes were left in place; audit for any rule with Effective_Grant_Type = 'Hierarchy'.

3.5 · LWC + Aura Controllers — the Reachability Problem

A common architectural error: building an internal-facing LWC, then later granting access to the guest profile for "convenience" without re-auditing the controller code. The component is reachable from a guest context. The controller code, written assuming an authenticated internal user, is now executing on behalf of an anonymous visitor.

The default-callable surface

  • Any @AuraEnabled method on an Apex class accessible to the guest profile is guest-callable
  • This includes methods on classes shipped by managed packages, if the guest profile has the package's class access
  • Visualforce remoting endpoints are similar: callable from any context with the page access
  • Custom REST endpoints (@RestResource) are governed by the URL mapping and class access; guest reachability requires explicit grant but is easy to add accidentally

Hardening pattern

  1. Class-level: with sharing + WITH USER_MODE on every SOQL. Default-mode Apex bypasses sharing; from a guest context, that is a critical risk of unintended full-organization data exposure.
  2. Explicit denial check. At the top of any guest-reachable @AuraEnabled method, validate the caller's expected context. Example: 
    @AuraEnabled
public static List<Case> getMyCases() {
    // Explicit guest-context denial unless the method is *intended* for guest use
    if (UserInfo.getUserType() == 'Guest') {
        // Either return only the records intended for guest exposure...
        return [SELECT Id, CaseNumber FROM Case
                WHERE IsPublished__c = true
                WITH USER_MODE
                LIMIT 50];
        // ... or throw, if the method is internal-only and shouldn't be guest-reachable at all:
        // throw new AuraHandledException('Access denied');
    }
    // Authenticated path
    return [SELECT Id, CaseNumber, ContactEmail FROM Case
            WHERE OwnerId = :UserInfo.getUserId() WITH USER_MODE LIMIT 50];
}
  3. Static-analysis gate. A CI check that flags any @AuraEnabled method on a class accessible to the guest profile that does not contain a UserInfo.getUserType() check or an explicit WITH USER_MODE SOQL. (Pillar 9 covers DevSecOps gates.)
  4. Reachability snapshot. Quarterly: dump the guest profile's class access list, diff against the prior quarter. Any added class triggers a controller review.

3.6 · Unauthenticated Endpoint Variants — DIVD-2026-00005

DIVD-2026-00005[13] documents "Salesforce Experience Cloud — Data Exposure via Misconfiguration" centered on Aura and Lightning Component endpoints (e.g., /s/sfsites/aura) reachable from the unauthenticated guest context. Where guest profile permissions and field-level security are insufficiently restrictive, an attacker can extract sensitive records by directly invoking these endpoints rather than going through the authored UI. (Adjacent: similar exposure surfaces include Salesforce's GraphQL endpoint where guest API access is enabled.) The pattern matches the SOQL-via-Aura case: enumerate the surface, query for records the guest user has been granted access to in error.

What to audit

  • Guest profile API access. The "API Enabled" system permission gates GraphQL too. Off by default; verify it is off for every guest profile.
  • Apex resolvers in @AuraEnabled methods returning GraphQL-shaped results. The same controller hardening as 3.5 applies.
  • UI Tier objects exposed via GraphQL. Standard Salesforce UI APIs that wrap GraphQL can expose more shape than expected; review the GraphQL schema accessible to the guest user (run an introspection query against your sandbox's guest endpoint).

3.7 · Public-Site Surface — Cache, URL, Search-Engine Exposure

The public face of Experience Cloud has its own attack surface beyond the API endpoints:

URL surface

  • Predictable record IDs in URLs. 18-character Salesforce IDs are quasi-sequential; URL guessing on public-site detail pages is feasible. Use friendly URLs / vanity slugs and validate the record's intended exposure on every render.
  • Search-engine indexing. Public site pages are indexable by default. Audit your robots.txt equivalent in the site's settings; verify cache responses to ?_= style cache-busters do not bypass guest scoping.
  • Custom domain (My Domain for Communities). Use a custom domain, not the default *.my.salesforce-experience.com — both for branding and for control over DNS / TLS / WAF.

Cache surface

  • Static resources accessed via guest-restricted profile are cached as private (browser-only) rather than CDN-shared
  • Switching a previously-unrestricted site to restricted has a 45-day cache-expiry window during which previously-cached content remains accessible — plan cutovers accordingly[24]

Audit pattern

  • Quarterly: Google / Bing site search of your public Experience Cloud domain, scanning for record-ID-shaped URLs that should not be indexed
  • Verify noindex headers on detail pages whose visibility depends on session state
  • Web Archive (archive.org) check for any historical exposure of records that should never have been public

3.8 · Automated Scanner + Public-Site Crawl Pattern

Manual quarterly review captures most of the value but misses drift between reviews. The pattern that catches drift is two coordinated scanners running on a shorter cadence:

Scanner A — Metadata Scanner (declarative drift)

Runs nightly. Pulls from Metadata API:

  • Every guest profile's full permission set (object, field, system, Apex, Visualforce, LWC)
  • Every guest user sharing rule
  • Every Custom Object and Custom Field FLS for the guest profile
  • Every Aura/LWC component access grant

Compares against an approved baseline manifest stored in version control. Any diff → alert + ticket. Approved changes update the baseline manifest via PR review (Pillar 9).

Scanner B — Public-Site Crawler (effective exposure)

Runs weekly. Walks the public site as an unauthenticated user:

  • Submits introspection-style queries against every Aura/LWC controller endpoint reachable from any guest-accessible page
  • Issues GraphQL introspection (where enabled) and queries each exposed type
  • Probes record-ID-shaped URLs across each accessible object's visible records, comparing returned field count and field names against the metadata baseline's expected exposure
  • Captures HTTP status, response body shape, and a hash of the response (not the data) for diff

Findings: any field returned that is not on the approved exposure baseline; any record count above the expected ceiling; any unexpected endpoint shape.

Cross-validation

Findings from the two scanners cross-reference: a metadata-scanner-only finding (config drift not yet reachable from the public site) is medium-severity; a public-site-crawler-only finding (data accessible that the metadata baseline does not predict) is critical — it means the configuration is doing something the audit did not foresee.

This is a generalized pattern (similar dual-agent scanning is used in DevSecOps repo-protection elsewhere in the document). It is not a Salesforce-shipped capability; it is a customer-side custom build, typically a few hundred lines of Node.js or Python plus a metadata snapshot in version control.

4.1 · Connected App → External Client App Transition (Spring '26)

Salesforce restricted Connected App creation as of Spring '26. Existing Connected Apps continue to work. New integrations should be built using External Client Apps (ECA) — a more granular, more auditable Connected App replacement.

What ECA changes

  • Per-app policies are richer. ECA exposes finer-grained scope, IP, and session policies
  • Configuration is split between metadata types. The app, its policies, and its OAuth settings are separate objects — deploy and audit them independently
  • Deprecation path: existing Connected Apps continue to function; new ones go through ECA. Treat ECA migration as part of the 12-month structural lane.

What stays the same

OAuth flows, scopes, refresh-token mechanics, and the OAuth Usage report all behave identically. Everything else in this pillar applies to both Connected Apps and ECAs.

4.3 · Block Uninstalled Connected Apps + Admin Pre-Approval

The default behavior this turns off

By default, Salesforce treats a Connected App's consumer_key (OAuth client_id) as globally addressable across orgs. When a user in your org follows an OAuth authorize URL whose client_id resolves to a Connected App registered in some other org, the platform auto-creates a "shadow" Connected App entry in your org keyed off that client_id, presents the consent screen, and (on user approval) issues a token. The app definition is essentially replicated into your org on first authorization, with no admin involvement. This auto-replication is the property UNC6040 / ShinyHunters-style vishing weaponized: register a malicious Connected App in a throwaway attacker-controlled org, then phone the victim through approving the OAuth verification code in your org. The platform performs the cross-org replication; the victim sees only a normal-looking consent screen.

The setting that turns it off

"Block authentication for uninstalled connected apps", in Setup → OAuth and OpenID Connect Settings. When enabled, the platform refuses to auto-create the shadow record; the OAuth request fails with an invalid_client-class error before the consent screen ever renders. The user sees a generic OAuth error page (no consent prompt, no app branding, nothing to click through). If you are watching for it, this is what a successful block looks like in the wild — train operators to recognize and report it rather than retry.

Status: default-on for most orgs since September 2025[6] via the "Block Authentication for Uninstalled Connected Apps" critical update. Orgs created after the rollout date inherit it on; some orgs created before may still have it off — verify rather than assume. This is the single highest-leverage control against the UNC6040 pattern: even if an attacker convinces a user to approve a malicious Connected App, the authorization fails at the platform layer because the app was never admin-approved in your org.

Verify it is on

  • Setup → OAuth and OpenID Connect Settings → "Block authentication for uninstalled connected apps" — toggle: enabled
  • For each Connected App you do use: Manage → Edit Policies → Permitted Users: "Admin approved users are pre-authorized" — not "All users may self-authorize"

The admin pre-approval contract

With pre-authorization, a user cannot grant the Connected App scopes themselves; only an admin assigns the app to a user via Permission Set or profile. This makes app authorization a reviewed, auditable, multi-step process — matching the 30-day quick-win lane.

High Assurance gate on Connected Apps

Per OAuth Policy: "High Assurance session required". Combined with FIDO2 (Pillar 1), this means even an admin pre-approving the app must touch a hardware key. Vishing attacks that try to bypass this require the attacker to physically possess the admin's hardware key — the practical impossibility that the entire identity pillar is built around.

What this control does not cover

The block is on the auto-replication path. It is not a defense against the cases where a Connected App definition is already legitimately present in your org. Specifically:

  • Managed-package Connected Apps. If your org has installed an AppExchange package that ships a Connected App, that app is installed (not "uninstalled") in your org — the block does not apply. A compromised ISV (UNC6395 / Salesloft Drift, August 2025) abuses this path, not the auto-replication path. Pillar 4.5 (AppExchange Security Review) and Pillar 4.6 (ISV repo compromise pattern) are the relevant defenses.
  • Connected Apps you registered yourself. Apps created in your org via Setup or via a metadata deploy are also "installed," and follow the per-app Permitted Users policy plus any High Assurance policy you set. The block is silent here.
  • External Client Apps (ECA). The Spring '26 successor primitive (Pillar 4.1) has its own equivalent control surface; verify the same posture there as you migrate.
  • Browser-extension session hijack (Pillar 4.8). A compromised extension reuses the user's existing authenticated session — no Connected App authorization is requested at all, so this control plane is bypassed entirely.

In short: "Block Uninstalled Connected Apps" closes the cross-org auto-replication door. The other doors — ISV supply chain, your own app inventory, browser-resident agents — need their own controls (Pillars 4.4–4.9).

4.4 · Refresh-Token TTL, Rotation, Revocation

Default OAuth policy gives refresh tokens an indefinite lifetime — a refresh token issued once persists until explicitly revoked or until the user logs out and the policy triggers expiry. This is the persistence mechanism the 2025 breach wave abused.

The hardening configuration

  • Refresh Token Expiration: 90 days or less. Tokens not used in 90 days expire; users re-authorize. Tradeoff: visible re-auth friction. Acceptable for most integrations.
  • Refresh Token Rotation: enabled. Each refresh issues a new refresh token; the old one is invalidated. A stolen refresh token is good for one use, then it's burned. Detection signal: any refresh-token reuse triggers an alert (the signature of a stolen token being used in parallel with the legitimate user).
  • Session expiration on logout: enabled — revokes refresh tokens on user logout
  • IP relaxation: disabled for high-trust apps — tokens only valid from the IP they were issued to

Revocation surface

  • OAuth Connected Apps page: revoke per-user / per-app
  • Connected Apps OAuth Usage: per-user revoke
  • User detail → Connected Apps: per-user revoke for that user's apps
  • Apex / Tooling API: programmatic revoke (incident response automation)

Pattern. An incident-response runbook that does the revoke programmatically across all users for a given Connected App. Pillar 8 covers IRP; the OAuth-revoke runbook is one of the high-velocity playbooks worth pre-building.

4.5 · AppExchange Security Review — Necessary, Not Sufficient

Salesforce's AppExchange Security Review[27] is a real, rigorous process. Passing it is necessary. It is not sufficient against supply-chain attacks. As Synexc put it after the August 2025 wave: "The uncomfortable truth is that you can pass a Salesforce security review and still be wide open to a SaaS supply-chain attack. Because the review is scoped to Salesforce the application, not Salesforce the ecosystem."[28]

What review covers

  • The package's metadata and Apex (USER_MODE / FLS / sharing / SOQL injection / XSS)
  • The package's external endpoints (Remote Site Settings, CSP Trusted Sites)
  • The package's identity model (Connected App scopes; auth flows)
  • OWASP-aligned static analysis

What review does not cover

  • The ISV's own production environment, CI/CD pipeline, GitHub repos
  • The ISV's customer-grant database (where customer refresh tokens are stored)
  • The ISV's internal security posture, employee MFA, device hygiene
  • Post-installation behavior over time (only the package's behavior at submission time is reviewed)

Customer-side controls that close the gap

  • Quarterly post-install package monitoring. InstalledPackage SOQL audit. New packages or version bumps trigger review.
  • ISV Connected App refresh-token rotation contract. Bake rotation cadence into procurement — "ISV must rotate refresh tokens every 90 days; ISV must publish breach response SLA".
  • Per-ISV scope minimization. Many ISV apps request scopes they don't need (full, refresh_token). Review and downgrade where possible.
  • Real-Time EM monitoring of ISV-shaped queries. ApiEvent correlated with the Connected App's client_id; baseline normal traffic; alert on anomalous bulk reads.

4.6 · ISV Repo Compromise Pattern (UNC6395 / Salesloft Drift)

The August 2025 incident is the canonical example: attackers compromised Salesloft's GitHub repositories[29] March–June 2025. The repos contained — or led to — the OAuth refresh tokens that the Drift integration had stored on behalf of its Salesforce customers. Attackers used those tokens to authenticate as the Drift app against 700+ Salesforce orgs, including Cloudflare, Zscaler, and Palo Alto Networks. Drift was pulled from AppExchange in August 2025; tokens were revoked.

The kill chain

  1. Attacker compromises ISV's GitHub repos (or CI/CD secrets, or developer workstation)
  2. Attacker locates ISV's Salesforce customer-grant database / OAuth token storage
  3. Attacker harvests refresh tokens
  4. Attacker exchanges refresh tokens for access tokens against each Salesforce org
  5. Attacker queries / extracts data, looking like the legitimate ISV's traffic
  6. (Detection comes from anomalous query volume, off-hours patterns, or the ISV publicly disclosing)

Customer-side resilience

  • Refresh-token rotation (4.4) limits the value of any one stolen token to 90 days max
  • Real-Time Event Monitoring baselines ISV traffic and alerts on anomalies
  • OAuth Usage attestation catches any token-active state that the app's recent activity pattern doesn't justify
  • ISV breach SLA in procurement contracts — ISVs commit to disclosing within 24 hours of detection

The architectural lesson. Treat any ISV with stored OAuth grants as a SOC-2-equivalent custodian of your data. Their security posture is your blast radius.

4.7 · Vishing → Malicious Connected App (UNC6040 Kill Chain)

The 2025 vishing wave [16][17] targeted English-speaking employees with calls impersonating IT support. Per primary reporting (Google Threat Intelligence Group + Mandiant[17]; Mitiga[29]) confirmed targets include Google itself, Cisco, Adidas, Qantas, Allianz Life, and LVMH-group brands (Louis Vuitton, Dior, Tiffany & Co.). Additional names that appear in secondary coverage but are not attributed in primary sources include Pandora, Chanel, and Starbucks Singapore — treat as unverified pending primary-source confirmation. Tracker: UNC6040 (Google Threat Intelligence Group designation). UNC6040 has publicly claimed affiliation with ShinyHunters; researchers also discuss overlap with Scattered Spider / Lapsus$ tradecraft, but those linkages are not all formally confirmed in primary threat-intel attributions and should not be conflated as a single ecosystem.

The kill chain

  1. Reconnaissance. Attacker harvests employee names + phone numbers (often from earlier Krebs-pattern Experience Cloud exposures — the data exposed in 2023 was used to fuel vishing in 2024–2025; the breaches compound)
  2. Voice phishing call. Attacker calls employee, claims to be IT, walks them through a "verification" flow on Salesforce login.salesforce.com
  3. Verification code. Attacker has triggered a Connected App authorization (Data Loader or a malicious lookalike); the verification code goes to the legitimate user, who reads it back over the phone
  4. Token issued. Salesforce issues an OAuth access token to the attacker's Data Loader instance, scoped to whatever the user could do
  5. Bulk extraction. Attacker runs Bulk API queries; data leaves; persistent refresh token enables continued access

Customer-side controls (every one of these breaks the chain)

  • Block Uninstalled Connected Apps (4.3) — the unknown Data Loader instance is refused at step 4
  • FIDO2 hardware key (Pillar 1) — verification cannot be approved over the phone
  • Admin pre-approval (4.3) — the user cannot self-authorize
  • High Assurance for Data Loader / Bulk API — the bulk-extract operation requires fresh hardware-key touch
  • Real-Time EM threshold alert on bulk read volume — even if other controls are bypassed, the extraction triggers a detection
  • Operator training that names the attack — "you will receive a call from someone claiming to be IT support; that person is an attacker; here is the script"

4.8 · Browser Extensions — the Invisible OAuth Bypass

Browser extensions are the most overlooked OAuth-grant equivalent: they ride the authenticated browser session, inheriting whatever permissions the user has. Salesforce cannot distinguish actions taken by the user from actions taken by an extension acting on the user's behalf. They do not appear in the OAuth Usage report. They do not appear in the Connected Apps list. They are invisible to all native Salesforce monitoring.

The December 2024 supply-chain attack compromised 33 Chrome extensions (Cyberhaven primary reporting; some industry coverage cited higher counts), stealing session cookies and credentials from 2.6 million users (per Cyberhaven primary reporting)[6][14]. None of those extensions had Salesforce-issued OAuth grants. They didn't need them.

Hardening levers (endpoint-side, not Salesforce-side)

  • Chrome Enterprise / Edge Enterprise / Safari MDM allowlist. Default-deny on extensions; allowlist a curated list. Configure via group policy / MDM
  • Dedicated browser profile for Salesforce. Zero extensions installed in the Salesforce-only profile. Operator training: do Salesforce work in this profile, no other browsing
  • EDR / MDM extension monitoring. CrowdStrike / SentinelOne / similar can track extension installations and alert on supply-chain CVEs
  • Quarterly extension audit. Endpoint-management report listing every extension on every endpoint; cross-reference against a CVE feed
  • Incident-response playbook for extension compromise. Force-logout all sessions, revoke OAuth tokens, change passwords, review Setup Audit Trail and Login History for the affected user, force re-MFA enrollment

The category lives outside Salesforce, but the breach is inside Salesforce. This is one of the rare pillar topics where the customer-side fix is entirely off-platform — and it must still be in the hardening plan.

4.9 · OAuth Usage Attestation + Dual-Agent Metadata Scan

Quarterly OAuth Usage attestation (the report)

Setup → Connected Apps OAuth Usage. The standard cadence:

  • Pull the report for the prior quarter
  • For each app: most-recent-use timestamp, user count, total token issuance
  • Cross-reference against the prior quarter; flag every app that appeared this quarter and was not in the prior quarter; flag every app that suddenly grew in user count by >25%
  • Verify each app has an active business owner; revoke apps without an owner
  • Verify each app's session policies are as expected; flag any change since prior quarter
  • Sign-off: dated, signed (electronic), retained

Continuous dual-agent metadata scan (the drift detector)

A pattern: two independent scanners watching the metadata for Connected App / External Client App drift. Cross-validation is the security feature.

  • Scanner A — pulls Metadata API: every ConnectedApp entity, every ExternalClientApp entity, full configuration. Diffs against an approved baseline manifest in version control
  • Scanner B — pulls runtime data: OauthToken, ConnectedApplication objects via SOQL. Detects state that the metadata snapshot would not predict (e.g., an app present at runtime that is not in the manifest, indicating manual creation that bypassed the deployment pipeline)
  • Cross-validator — A says "manifest-only", B says "runtime-only" — either direction is a finding. Agreement (both clean / both flag): expected. Divergence: investigate
  • Tamper-evidence — scan results stored in an append-only HMAC-signed log; operator review acknowledged with FIDO2 touch

Same dual-scanner pattern is applied to git repositories in Pillar 9 (DevSecOps). The principle transfers: two independent perspectives, with cross-validation, are significantly more resilient to fool than one.

5 · API, mTLS & Certificate Rotation

Integrations need credentials and certificates to talk to external systems. Where you store them and how often you rotate them are the two decisions that matter. 5.1 · Named Credentials & External Credentials

Named Credentials (NC) and External Credentials (EC) are the only sanctioned places for integration secrets. They are auditable, rotatable, and isolated from your codebase.

Anti-patterns (every one of these is a finding)

  • API keys / passwords stored in Custom Settings or Custom Metadata Type fields
  • Hardcoded secrets in Apex string literals or test classes
  • Secrets in Static Resources (zip / JSON) shipped with packages
  • Secrets passed in URL query parameters to outbound callouts
  • Secrets in Visualforce page expressions

Named Credentials

  • Hold the endpoint URL + auth (OAuth, JWT bearer, password, basic, AWS SigV4, certificate)
  • Apex callout uses callout:My_Named_Cred/path — no secret in code
  • Setup Audit Trail logs every change to a Named Credential (creation, rotation, deletion)
  • Permission Set grants determine which users can callout via which NC

External Credentials

  • Newer, more granular than Named Credentials
  • Separates the credential (auth + secret) from the endpoint (Named Principal)
  • Supports Per-User Named Principals: each user has their own credential, scoped to them alone — no shared integration secret
  • Supports multiple credentials per endpoint for different user populations

Per-user named principal pattern

When the external system supports it, give each user their own credential. Stolen credential = one user's blast radius, not the whole integration's. Audit logs at the external system attribute actions to specific users. Use per-user principals for any integration that touches PII or executes business operations.

5.2 · Mutual TLS — Outbound and Inbound

Standard TLS authenticates the server to the client. Mutual TLS (mTLS) additionally authenticates the client to the server — both sides present certificates and validate the other. This is the right answer for high-trust integrations: financial settlement, regulated reporting, inter-system signed messaging.

Outbound mTLS (Salesforce calling external)

  • Setup → Certificate and Key Management → create or upload a client cert
  • Named Credential → configure to use the client cert for outbound auth
  • External system validates client cert against its trust store
  • Salesforce validates server cert against its trust store (default Salesforce-managed root chain)

Inbound mTLS (external calling Salesforce)

  • Setup → Mutual Authentication Certs[30] — upload the CA chain that signs the inbound clients' certs
  • Profile / Permission Set permission: Enforce SSL/TLS Mutual Authentication
  • API endpoints validate the inbound client's cert against the uploaded CA
  • Each inbound client gets a distinct cert — per-client revocability

2026 dual-use cert ban impact

Per enosix[31]: Chrome will enforce a strict ban on dual-use certificates — certs used for both server authentication and client authentication. This affects how customers implement mTLS. Migration: issue separate server-auth and client-auth certs from your CA; do not reuse one cert for both purposes.

  • Self-signed certs you uploaded — not in scope; manage rotation yourself

5.4 · Integration Users & Per-User Named Principals

The single most powerful integration-security pattern is also the simplest: one integration user per integration, with the minimum permissions required for that integration's job. No human ever logs in as the integration user. The integration user has no UI access. Its API calls are observable in event logs, distinct from human user activity.

Integration user setup

  • License: Salesforce Integration license (lower-cost, API-only) where eligible
  • Profile: API-only (Setup → Profiles → clone Standard User → remove UI access)
  • Permission Set Group: integration-specific, scoped to the objects + fields the integration touches
  • "API Enabled" yes; "Modify All Data" no; "View All Data" no; specific object permissions only
  • Login IP Range: locked to the integration source's static IPs
  • MFA: yes — but via JWT Bearer flow (the cert is the second factor)

Why one-per-integration matters

  • Blast radius isolation. Compromised credential = one integration's data, not all of it
  • Observable. Login History and Real-Time EM filters by username; integration anomalies stand out
  • Revocable. Disabling one integration is one user deactivation, no other side-effects
  • Audit-friendly. Map "integration user" to "integration" 1:1 for quarterly attestation

Per-user named principal — one level deeper

Where the external system supports it, individual end-users get their own credential to the external system, not a shared integration credential. Combined with External Credentials (5.1), this gives user-level audit trail at the external system and blast-radius isolation if any one user's credential is leaked.

5.5 · API Client Allowlist + Pub/Sub API Hardening

API client allowlisting

  • Login IP Ranges on the integration user's profile / Permission Set
  • Connected App / ECA IP Restriction — per-app IP enforcement
  • Trusted IP Ranges at the org level (skip Identity Verification for these IPs)
  • Block by Default: prefer locked-down with explicit allowlist over open-with-blocklist

Pub/Sub API (event-driven integrations)

The Pub/Sub API[33] is the modern replacement for Streaming API / CometD for Platform Events and Change Data Capture. gRPC-based. Token-authenticated.

  • Use a dedicated integration user for Pub/Sub subscribers
  • Scope Permission Sets to the specific Platform Events / CDC channels needed (not "subscribe to all")
  • Validate the published event content in the subscriber — do not trust event payloads as authoritative
  • Pub/Sub events are observable in Real-Time EM (ApiEvent + StreamingChannelEvent) — baseline normal subscriber rate, alert on drops (could indicate stolen credential being used elsewhere)

6.1 · Apex Run Modes — USER_MODE as the Default

The hierarchy was covered in Pillar 2.6. The rule for new code: WITH USER_MODE on every SOQL, AccessLevel.USER_MODE on every DML, with sharing or inherited sharing on every class. Default System-mode Apex is the historical default and the historical bug source.

Migration order for legacy code

  2. Classes invoked from Visualforce / LWC reachable from public sites
  3. Classes with @AuraEnabled methods
  4. Custom REST resources
  5. All other Apex classes touching sensitive objects
  6. Bulk-update scripts and batch jobs (often last; usually require system mode but rarely justify it)

6.2 · SOQL Injection — Bind Variables, Not Concatenation

Salesforce's official position[34]: avoid dynamic SOQL where static SOQL with bind variables works. When dynamic SOQL is required, use String.escapeSingleQuotes() on user input. Bind variables are preferred.

Patterns

  • Static SOQL with bind — the default: [SELECT Id FROM Contact WHERE Name = :userInput WITH USER_MODE]
  • Dynamic SOQL with typed bind — for non-string types: build the query string, use Database.queryWithBinds(query, bindMap, AccessLevel.USER_MODE)
  • escapeSingleQuotes — legacy fallback when neither of the above fits, e.g., column-name driven dynamic ORDER BY

SOQL injection lives in the OWASP Top 10[35]; treat it as a deployment-blocking finding in DevSecOps gates (Pillar 9).

6.3 · LWC + Visualforce XSS, Sanitization, Manual DOM

LWC

  • Lightning Web Security (LWS) sandboxes components by default; sanitization is automatic for normal binding
  • lwc:dom="manual" opts out of the sanitizer — required for some integrations but a magnet for XSS bugs; minimize use, sanitize manually before innerHTML
  • lightning-formatted-rich-text auto-sanitizes; prefer it over hand-rolled HTML rendering
  • External scripts in LWC require Trusted CSP entries; review the trust list quarterly

Visualforce

  • Standard <apex:*> tags include built-in HTML escape; do not escape="false" without justification
  • Formula tags like {!$Request.*} are XSS magnets; use SUBSTITUTE() or encoding functions ($URL_ENCODE, $JSENCODE) where they appear in URLs / scripts / attributes
  • JavaScript blocks inside Visualforce: developer-managed sanitization required; LWS does not protect

6.4 · CSRF Defaults and the Constructor-DML Anti-Pattern

Salesforce automatically includes anti-CSRF tokens on standard pages and validates them on form submission. The known footgun: do not perform DML in a Visualforce page constructor or LWC @wire function. CSRF protection wraps user-initiated actions; constructor code runs without that protection.

Specifically avoid

  • DML in a Visualforce page constructor (executes on GET; bypasses CSRF token check)
  • DML in an LWC connectedCallback with no user gesture
  • DML in @AuraEnabled(cacheable=true) methods (cacheable methods cannot DML; this is enforced)
  • Any "side effect on page load" pattern — defer to user-initiated action handler

6.5 · Flow Security — Run Context and the Guest-Accessible Problem

Flow is the most common workflow primitive in modern Salesforce orgs. It is also the most commonly misunderstood. "How does this Flow run?" is the question that determines whether the Flow respects sharing and FLS or ignores them entirely.

Run-context decision tree

Flow typeDefault run contextOverride
Record-Triggered FlowSystem context (no sharing, no FLS)Set "How to Run the Flow" to "User context, with sharing"
Schedule-Triggered FlowSystem contextSystem context only
Autolaunched Flow (subflow)Inherits caller's contextForce user context per subflow

Hardening rules

  • Default to user context for Record-Triggered Flows that touch user-visible objects. Use system context only when the Flow's purpose is privilege escalation (e.g., system-managed audit trail row inserts) and document the justification.
  • Invocable Apex called from Flow inherits the Flow's run context — system-context Flow with system-context Apex is a double bypass
  • Guest-accessible Flows are the high-risk surface. Flows reachable from a public Experience Cloud page execute in the guest user's context. Audit them with the same rigor as Pillar 3's @AuraEnabled review.
  • Flow with no Apex actions, but with Get Records / Update Records elements that ignore sharing is the silent leak path. The Flow Builder UI does not warn you; Setup Audit Trail records the creation but does not flag the run-context.

Auditing Flow run-context

  • Metadata API: FlowDefinition / Flow entities expose processMetadataValues with RunInMode — query for system-context Flows
  • Quarterly attestation: enumerate all Flows running in system context, justify each one
  • Static-analysis CI gate: any new Flow PR that introduces a system-context Record-Triggered Flow requires explicit reviewer sign-off

6.6 · Shadow Flow / Outbound Messages — the Silent Exfil Vector

Outbound Messages and Flows that call external endpoints can become silent exfiltration channels. A privilege-escalated user (or a compromised admin account) can create an Outbound Message or a Flow with an HTTP callout that ships records to an attacker-controlled endpoint, silently, on every record change. This is the OWASP-equivalent of a stored XSS in the metadata layer.

Audit pattern

  • Metadata API: enumerate every WorkflowOutboundMessage, every Flow with an HTTP callout (actionType = "apex" with a callout-class action), every Apex class containing HttpRequest + setEndpoint
  • Cross-reference each external endpoint against the org's Remote Site Settings + CSP Trusted Sites inventory; any callout to a domain not in the inventory is a finding
  • Cross-reference against an approved-integrations registry (custom metadata or version-controlled document); flag every endpoint not on the registry
  • This is a CI gate in mature orgs (Pillar 9): PRs that add HTTP callouts must list the new endpoint and the business justification

Detection

  • Real-Time EM: ApiEvent captures inbound REST traffic; outbound callouts are not directly captured, but Apex callout latency spikes show in ApexExecutionEvent — baseline normal callout patterns
  • Outbound Messages have their own retry log; large delivery queues to unknown endpoints are a signal

6.7 · Email-to-Case / Web-to-Lead / Web-to-Case Intake Hardening

The intake surface accepts data from anyone on the internet. Treat it accordingly.

Email-to-Case

  • SPF / DKIM / DMARC on the receiving domain — reject spoofed senders before the email reaches Salesforce
  • Inbound Email Service Apex handlers are server-side; treat email body and attachments as untrusted
  • File upload size and type limits at the Email Service definition
  • File-upload malware scanning — Salesforce does not scan attachments by default; integrate with a malware-scan service via Apex callout, or quarantine attachments to a holding object until scanned
  • HTML email rendering — Visualforce Email templates with user-controlled merge fields are an XSS vector if rendered in agent UIs; sanitize

Web-to-Lead / Web-to-Case

  • Form input validation at submission; Salesforce will accept whatever you POST
  • CAPTCHA on public forms — without it, your Lead/Case object becomes a spam dump
  • Hidden field tampering — never trust hidden fields in Web-to-X forms; validate on the server
  • Prompt-injection content in form fields per WithSecure 2026[15] — user-submitted content reaches AI agents; scrub or quarantine before AI consumption (Pillar 10)
  • Rate limiting at the WAF / CDN layer in front of the form endpoint

SPF / DKIM / DMARC

  • SPF: declare which servers are authorized to send mail for your domain; receivers reject mail from others claiming your domain
  • DKIM: cryptographic signature on outbound mail; receivers verify the signature
  • DMARC: tells receivers what to do with mail that fails SPF/DKIM (quarantine, reject); reporting addresses for delivery telemetry
  • For Salesforce-sent mail, configure DKIM keys in Setup → Email → DKIM Keys

7.5 · Sandbox Security & Data Mask

Sandbox PII is production PII. A Full Sandbox refreshed last week contains every record from production. Sandbox users are typically less rigorously administered; sandbox MFA enforcement is sometimes weaker; sandbox API integrations are sometimes less monitored. The result: sandbox is often the easiest path to production data.

Hardening levers

  • Salesforce Data Mask — anonymizes PII in non-production sandboxes; pattern-based or random replacement; deterministic mode for cross-sandbox referential integrity
  • Sandbox refresh governance — refresh cadence requires post-refresh hardening: re-MFA verification, integration-user re-provisioning, masked data verification before opening to Dev/UAT users
  • MFA enforcement parity — sandbox profiles enforce the same MFA / FIDO2 policy as production
  • Lower-env credential isolation — integration users in sandbox use distinct JWT keys / OAuth client_id from production; never share secrets across environments
  • External-system isolation — sandbox Named Credentials point to sandbox-equivalent external systems, not production endpoints

7.6 · Backup, Recovery, Ransomware Survival

Salesforce's recycle bin is not a backup. The Weekly Data Export tool is not a backup — it caps out, lacks metadata, and has no restore tooling. Real backup requires a real product (Salesforce Backup & Restore or third-party: OwnBackup, Spanning, Odaseva, AvePoint).

Recovery scope

  • Data: records and field history
  • Files: ContentVersion, Attachments, Documents
  • Metadata: objects, fields, Apex, Flows, profiles, permission sets, sharing, page layouts
  • Configuration: Connected Apps, Auth Providers, Named Credentials (without secrets), validation rules

Hardening of the backup itself

  • Isolated backup account — not a daily-use admin; FIDO2-only; Login IP locked to backup-runner host; quarterly attestation
  • Encrypted at rest in the backup store — customer-managed key
  • Immutable / versioned — ransomware that compromises Salesforce should not be able to overwrite / delete the backups; air-gapped or write-once storage
  • Restore testing — quarterly drill: pick a non-trivial restore (full object, point-in-time field history); document time-to-recover
  • BCP ownership — named owner, documented runbook, executive escalation path

Recycle Bin and Data Export limits

  • Recycle Bin retains deleted records for 15 days; capacity ~25x storage
  • Data Export (Setup) can export weekly/monthly; throttled; not suitable as primary backup
  • Use these as "free baseline" only; not a substitute for backup product

7.8 · Mask vs. Encrypt vs. Delete — Lifecycle

The four operations on data form a hierarchy of irreversibility:

  1. Encrypt — reversible with the key; data still present
  2. Mask — replace plaintext with consistent fake data (sandbox use case); reversible only via mapping table you control
  3. Anonymize — replace with content that cannot reconstruct the original; not reversible
  4. Delete — record gone; in Salesforce, soft-delete then hard-delete; honor recycle bin emptying for true deletion

Each operation matches a different lifecycle state. GDPR right-to-be-forgotten (7.9) requires "delete or anonymize"; "encrypt" is not sufficient.

7.9 · GDPR, CCPA, EU AI Act — What Hardening Owes Compliance

  • EU AI Act (effective 2025–2026): high-risk AI systems require risk management, data governance, human oversight, transparency. Salesforce-side AI (Einstein, Agentforce) inherits customer-side governance for any in-scope use case — classification + audit + human-in-loop are the levers (Pillar 10 covers AI-specific governance).
  • Industry-specific: HIPAA (PHI), PCI DSS (cardholder), GLBA / SOX (financial), FERPA (education) — each adds field-level encryption + audit + access-control requirements that this pillar's hardening provides the platform for

8.3 · Real-Time Event Monitoring & Retention Reality

Real-Time Event Monitoring is the customer-side telemetry surface: standard event types streaming to SIEM, queryable Event Log Objects with retention up to 30 days. Plan for 30-day retention in Salesforce; ship to SIEM for longer.

Event types worth monitoring

  • LoginEvent: every login; correlate with Login History
  • ReportEvent: report runs; chunked output
  • ListViewEvent: list view runs
  • ApiEvent: every inbound REST/SOAP API call (this is the catch-all for inbound API activity; not Apex outbound callouts)
  • ApiAnomalyEvent: Threat-Detection-flagged anomalous API behavior
  • BulkApiResultEvent: Bulk API operations — the UNC6040 detection hotspot
  • UriEvent: page visits; gives you a sense of in-app navigation
  • LogoutEvent: end-of-session signal; Logout Event Triggers can run Apex
  • TransactionSecurityEvent: every Transaction Security action taken
  • ApexExecutionEvent: Apex performance + scope; large baseline

Caveats

  • Event Log Objects: SOQL only (no relationship queries, no HAVING, no OFFSET); 30-day retention; available only on Hyperforce
  • Time-window queries: up to 15 days at a time; DAY_ONLY() required
  • For longer retention or advanced queries, ship to SIEM (8.7)

8.4 · Threat Detection — What It Covers (Shield / Event Monitoring)

Threat Detection is the structured anomaly-event surface that Salesforce ships as part of the Real-Time Event Monitoring / Shield license — not a free baseline. The free baseline is Login History (which shows basic new-device flags and suspicious-login warnings) plus Setup Audit Trail. Threat Detection adds machine-learning-tuned anomaly events that fire on specific high-signal patterns and that Transaction Security policies can subscribe to for real-time enforcement.

Detection categories (events emitted)

  • Anomalous report and data exports — off-baseline export volumes / patterns
  • Session hijacking — multiple sessions from divergent geographies in close succession
  • Credential stuffing — failed-login pattern matching automated attempts
  • Anomalous API access — off-baseline API call volumes from individual users

Findings appear in Real-Time EM as structured event records (e.g., ApiAnomalyEvent, CredentialStuffingEvent, ReportAnomalyEvent, SessionHijackingEvent, GuestUserAnomalyEvent). Subscribe via the Pub/Sub API (gRPC streaming to a SIEM-side consumer), via Apex Subscribers on the platform event objects, or via Transaction Security policies for inline Block / MFA / Notify actions. (Logout Event Triggers fire on logout specifically — useful for tying anomaly cleanup to session-end, but not a generic subscription path.) Threat Detection is intentionally tuned conservatively; expect to lower the threshold for events that are noisy in your specific traffic pattern.

8.5 · Enhanced Transaction Security — Block / MFA / Notify

Transaction Security turns events into real-time enforcement: for events the platform can intercept synchronously (LoginEvent, ApiEvent, BulkApiResultEvent, ReportEvent, et al.), a matching policy holds the in-flight request and takes one of three actions — Block, require Multi-Factor Authentication, or Notify.

How "MFA" actually enforces. The MFA action does not inject a custom prompt into the calling UI. It redirects the request to Salesforce's stock Verify Your Identity page — the same High Assurance step-up flow used by Session Security Levels. On successful verification the session is raised to High Assurance and the original request resumes. Practical consequence: MFA enforcement requires a browser request path. For headless flows (Bulk API export, REST API integrations, server-to-server jobs) there is no UI to redirect to, so MFA degrades to a refusal — in those cases use Block as the action. See Enhanced Transaction Security — Actions & Notifications ↗.

8.6 · Incident Response Plan + AI Agent Compromise Scenario

Standard 5-phase IR loop applies to most Salesforce incidents:

  1. Contain — revoke OAuth tokens, kill sessions, deactivate user, disable Connected App, flip kill-switch
  2. Identify — pull Setup Audit / Login History / Real-Time EM for the incident window; scope
  3. Eradicate — rotate JWT secrets / certs / passwords, remove backdoor metadata, redeploy from known-good
  4. Notify — internal stakeholders, customers, regulators per applicable timelines
  5. Post-Mortem — root cause, detection gap, response time; update runbooks; tune detection

AI agent compromise — the silent-compromise indicators

A compromised AI agent (Agentforce, Einstein, custom Connected App AI integration) can produce outputs that look like normal authorized operation. Classical detection signals (auth failures, error spikes, infrastructure health) all stay green. The detection signals are different.

Threat classDetection signal
Prompt-injection manipulation (web form → agent)Filter-flag rate spike on intake objects; deterministic re-run hash mismatch
Fabricated agent decisionsOutput-hash deviation vs. deterministic re-run
Agent credential exfiltrationService-account usage outside expected job context (e.g., on-host audit log anomaly)
Eval bypassDecision-log entries with no corresponding evaluation result within SLA
Provider manipulationCross-provider divergence monitor (run two providers; flag major divergence)

Detection rule. Any two concurrent silent-compromise indicators ⇒ treat as Suspected AI Agent Compromise; full IRP loop, with AI-specific eradication (suspend agent service accounts, rebuild from last known-good image, rotate secrets).

The full pattern is generalized in this document from operator-security practice; the implementation surface in Salesforce uses Real-Time EM events + custom Agent_Decision_Log__c + deterministic re-run jobs + dual-provider failover (Pillar 10 covers this).

9 · DevSecOps for DX & Org Lifecycle

The path code takes from a developer's laptop to your production Salesforce org is itself an attack surface. Secrets accidentally committed to a Git repository, weak permissions on a development environment, or a deployment with no second reviewer — each is a 2025-pattern breach waiting to happen. The August 2025 Salesloft Drift incident traced exactly this route. The fix is to treat the deployment pipeline like a high-trust integration: gated, monitored, multi-reviewer.

  • No long-lived secrets in deployment pipelines or Git repos — use short-lived federated authentication (your CI system mints a token at deploy time and discards it)
  • Automated security checks (PMD, SFDX Scanner) gate every deployment; security findings block the merge until they're addressed
  • Modern Salesforce deployment units with cryptographic signing on every promotion to production
  • Two-reviewer minimum on every production deployment; high-risk changes (sharing model, profiles) require additional sign-off
  • Sandbox refresh follows a hardening checklist (data masked, integration users re-provisioned, MFA verified) before users get access

9.1 · CI/CD Secret Management

Anti-patterns

  • SFDX auth URL committed to Git (the most common SFDX-era leak; instantly revoke if found in repo)
  • JWT private key in CI runner environment variables (capturable by any workflow on the runner)
  • Single shared service account for "all CI/CD" across multiple orgs (blast radius = all orgs)
  • Long-lived credentials with no rotation

Hardening pattern

  • OIDC-based federation for CI providers that support it (GitHub Actions, GitLab) — CI runner exchanges its OIDC token for a short-lived Salesforce session via JWT bearer flow; no long-lived secret in the runner
  • Per-org service account — one CI integration user per Salesforce org; rotate independently
  • Per-environment scope — Dev / UAT / Prod CI runners have distinct credentials; promotion across environments is a separate approval
  • Secrets in vaults, not env vars — HashiCorp Vault, AWS Secrets Manager, GitHub OIDC + AWS STS, GCP Secret Manager — secrets pulled at runtime, never committed, never in plaintext env
  • Audit log of secret access — the vault records who pulled what when

9.2 · Static Analysis as a Gate

Tools

  • PMD with the Apex rules — standard for Apex code quality and security
  • SFDX Scanner — Salesforce-published scanner; wraps PMD + ESLint + RetireJS + custom Salesforce rules
  • ESLint (with @lwc/eslint-plugin-lwc) — LWC-specific code quality
  • Custom rules — org-specific patterns (e.g., flag every without sharing, every @AuraEnabled on a guest-accessible class without explicit type check)

Gate placement

  • Pre-commit hook (developer feedback fast)
  • PR check (block merge until clean)
  • Pre-deploy CI step (block deployment to UAT / Prod)
  • Post-deploy verification (run scanner against the deployed code; catch drift between source and deployed)

Severity policy

  • Critical / High — block merge and deploy
  • Medium — require reviewer acknowledgment
  • Low — track in backlog; review quarterly

9.3 · Unlocked Packages + Signed Package Enforcement

Unlocked packages are the modern Salesforce DX deployment unit. Signing them adds a supply-chain integrity check: the deployed package is verifiably the one your CI built, with no tampering in flight.

  • Use Salesforce DX scratch orgs as the build environment; scratch org reset on every build means clean state
  • Promote package versions through Dev → UAT → Prod with progressively stricter approvers
  • Signing: hash the package version metadata; sign with a private key held only in the deployment vault; verify on install
  • Reject unsigned packages at the deployment gate

9.4 · Deployment Approval Workflow

  • 2-reviewer minimum for any deployment to Prod (1 architect + 1 admin/QA at minimum)
  • Approval recorded with FIDO2 hardware-key touch (Pillar 1.8 Tier 2 classification)
  • Approval log HMAC-chained for tamper evidence (each approval references the prior approval's hash; tampering with one approval breaks the chain)
  • Auto-revert on test failure within window (e.g., if Apex tests in the destination fall below 90% within 10 minutes of deploy, auto-revert)
  • Change Advisory Board (CAB) for high-risk changes (sharing changes, profile changes, security-impactful PSG changes)

9.5 · Metadata Git-Repo Dual-Agent Scanning

A pattern adapted from operator-security practice: two independent scanners watching the metadata repo from different perspectives, with a cross-validator that flags divergence as automatically critical.

Scanner Alpha — diff-based (changes only)

Walks git diff between the last approved scan and HEAD. Eight attack vectors:

  1. Privilege escalation — new Permission Set with elevated rights; new Profile permission grants; modifyAllRecords additions
  2. Backdoor routes — new @RestResource URLs not in the API contract; @AuraEnabled on guest-reachable class
  3. Sharing weakening — OWD changes from Private to Public; new guest sharing rules; sharing rule scope expansion
  4. Metadata tampering — changes to deployed-baseline objects without corresponding approved manifest update
  5. Dependency poisoning — package.json / sfdx-project.json changes adding unfamiliar dependencies
  6. Config injection — new Custom Settings or Custom Metadata values referencing hardcoded URLs / IPs / API keys
  7. Credential leak — pattern-matched JWT / cert / API-key shapes in any committed file
  8. Auth bypass — weakened requireAuth shapes in custom controllers; new public site URL pattern

Scanner Beta — static-pattern (current state)

Walks the entire repo, not just diffs. Eight overlapping attack vectors aimed at structural weaknesses regardless of when introduced. Catches patterns that pre-date the diff window.

Cross-validator

  • Both clean — expected; pass
  • Both flag same issue — high-confidence finding
  • Alpha-only — possible new issue not yet propagated; medium-confidence
  • Beta-only — pre-existing structural issue; medium-confidence
  • Divergence on the same code area — auto-CRITICAL; manual review mandatory

Tamper-evidence

Scan results in HMAC-chained log; operator review recorded with FIDO2 touch. The log itself is inspected by both scanners on each run — recursion that catches tampering with the log itself.

9.6 · Sandbox Refresh Governance

A sandbox refresh imports production data and metadata. Post-refresh, the sandbox must be re-hardened before users get access. The runbook:

  1. Run Data Mask on the refreshed sandbox before any user logs in — PII anonymized
  2. Re-provision integration users with sandbox-specific JWT keys / OAuth client_ids; never inherit production secrets
  3. Verify MFA / FIDO2 enrollment for sandbox users — profiles inherit production defaults but user-level MFA is per-environment
  4. Lock Login IP Ranges to sandbox-allowed sources
  5. Disable production-pointing integrations — Named Credentials updated to sandbox endpoints
  6. Verify masked data — sample-query each Restricted-classified field; confirm masked values returned
  7. Open access only after the checklist completes; deploy a "Sandbox Hardening Verified" custom setting that gates user-facing flows

10.3 · Trust Layer Pattern

Salesforce's Einstein Trust Layer protects platform-side AI. The customer-side equivalent for AI tools you use against your own org:

  • Zero retention — provider does not retain prompt or response (Anthropic's enterprise tier; OpenAI ZDR offering); confirm in writing in the contract
  • PII scrubbing outbound — before sending to a model, replace PII with typed placeholders ({contact_email_1}, {record_id_1}); never let real PII cross the trust boundary
  • Trust-boundary log — record every outbound call with HMAC tamper evidence; audit-friendly
  • Deterministic re-run — for high-stakes outputs (e.g., a flagged security finding), run the same scrubbed prompt twice (or once on each provider); store the response hashes; deviation triggers manual review
  • Dual-provider failover — primary + secondary; circuit breaker on outage; auto-fallback

The pattern is not Salesforce-specific; it is a customer-side data-handling discipline that applies to every AI use case in this pillar.

A.1 Scenario A — Vishing → OAuth grant abuse (UNC6040 pattern)

Trigger: A user reports an "IT support" call that walked them through a Salesforce verification flow; or Real-Time EM signals an unexpected Connected App authorization followed by Bulk API activity from an unfamiliar Data Loader instance.

Detection signals

  • LoginEvent: Application = 'Salesforce Data Loader' from a previously-unseen IP
  • BulkApiResultEvent: RowsProcessed spike from the affected user within 60 minutes of login
  • OAuth Usage: a freshly-authorized Connected App with no business owner
  • User report (out-of-band) of a suspicious phone call

Containment (target: complete in 15 minutes)

  1. Setup → Connected Apps OAuth Usage → locate the offending app for the user → Revoke.
  2. Setup → Users → the affected user → Freeze (do not deactivate yet; freeze preserves session forensics).
  3. Setup → Connected Apps → the malicious app's Manage page → Block for the entire org.
  4. Force-end all sessions for the user via Users → the user → "End Selected Session" against every active row.
  5. If the user's password may have been disclosed: trigger password reset.

Identify (target: 1 hour)

// Bulk API activity by the affected user in the last 24h
SELECT EventDate, Username, RowsProcessed, OperationType, SourceIp
FROM BulkApiResultEvent
WHERE Username = 'AFFECTED_USER@example.com' AND EventDate = LAST_N_DAYS:1
ORDER BY EventDate DESC

// All login events for the user, including geolocation
// (Lead with EventDate; wrapping CreatedDate in DAY_ONLY() disables the index.)
SELECT EventDate, Username, SourceIp, LoginGeoId, LoginType, Status
FROM LoginEvent
WHERE EventDate = LAST_N_DAYS:7 AND Username = 'AFFECTED_USER@example.com'

// OAuth grants by this user
SELECT Id, AppName, LastUsedDate, UseCount FROM OauthToken
WHERE UserId = 'USER_ID'

Eradicate

  • Permanently revoke the malicious Connected App. If it was uninstalled, verify it is on the Block list.
  • Reissue MFA enrollment for the user; require FIDO2 hardware key.
  • Review whether any records were modified during the access window; restore from Field Audit Trail or backup if so.

A.2 Scenario B — ISV / Connected App compromise (UNC6395 / Drift pattern)

Trigger: ISV publicly discloses a breach (or pulls their app from AppExchange); Real-Time EM shows anomalous query volume from the ISV's Connected App; security advisory is published.

Detection signals

  • ISV public disclosure or AppExchange listing pulled
  • OAuth Usage: the ISV's app shows token activity outside business hours or from new IP ranges
  • ApiEvent: query patterns deviating from the ISV's documented behavior

Containment (target: 15 minutes)

  1. Setup → Connected Apps OAuth Usage → locate the ISV's app → Revoke All (revokes all tokens, all users).
  2. Setup → Connected Apps → the ISV's app's Manage page → set Permitted Users to Admin Approved Users Are Pre-Authorized with no users assigned (effectively disables it).
  3. If the ISV maintains a webhook or Pub/Sub subscription, disable the corresponding Platform Event subscription.
  4. Notify your ISV procurement / vendor-management contact.

Identify

// All activity by the ISV's Connected App over the last 90 days
// (Lead with the indexed EventDate range; ConnectedAppId narrows it.)
SELECT EventDate, Username, ApiVersion, Operation, RowsProcessed
FROM ApiEvent
WHERE EventDate = LAST_N_DAYS:90 AND ConnectedAppId = 'ISV_APP_ID'
ORDER BY EventDate DESC

// All users who had granted the ISV
SELECT UserId, LastUsedDate FROM OauthToken WHERE AppName = 'ISV_APP_NAME'

Eradicate

  • Hold off on re-enabling the ISV's app until they publish a remediation report and pass an independent post-breach review.
  • If the ISV's grants stored elsewhere (refresh tokens, JWT keys), rotate any shared secrets.
  • If your contract with the ISV included an SLA on breach notification, evaluate whether they met it; document.

Notify

If your customers' data was processed by the ISV during the breach window, notification cascades to them. Coordinate with legal counsel; refer to Appendix O for jurisdictional timing.

A.3 Scenario C — Experience Cloud guest profile exposure (Krebs / DIVD pattern)

Trigger: Independent researcher disclosure; Google search reveals public-site URLs exposing record details; Pillar 3.8 dual-agent scanner emits a critical-severity finding.

Detection signals

  • Pillar 3.8 scanner: scanner-beta crawl returns records with fields beyond the approved baseline
  • Search-engine cache returns indexed pages with PII or record-IDs visible
  • Researcher report (often via security@ alias)

Containment (target: 30 minutes — takes longer than Scenarios A/B because cache invalidation is involved)

  1. Setup → Profiles → the affected guest user profile → turn off API Enabled, View All Users, all Run/Export Reports permissions.
  2. Object permissions on the guest profile: revoke any object that should not be guest-readable.
  3. Setup → Sharing Settings → remove or narrow every guest user sharing rule. (Document each removal in the incident ticket.)
  4. If the issue is via an Apex class accessible to guest: remove the class from the guest profile's Apex class access list.
  5. Site cache: per Pillar 3.7, expect a cache-invalidation lag for static resources. Force-refresh CDN if you control one.

Identify

  • Run scanner-alpha (metadata diff) and scanner-beta (crawl) to enumerate all currently-exposed fields and records.
  • Cross-check Field Audit Trail: which records were created or modified by the guest user during the exposure window?
  • Search engine cache: enumerate every URL indexed; request removal via Search Console.

Notify

Customer / data-subject notification almost always required. Refer to Appendix O; coordinate with legal counsel.

Evidence preservation

  • Snapshot the guest profile metadata XML BEFORE remediation (so the original-state can be reconstructed for forensics)
  • Snapshot every guest-accessible Apex class
  • Web Archive any indexed pages showing exposure (or capture them yourself before they're recrawled)

A.4 Scenario D — Browser-extension session hijack

Trigger: EDR / MDM detects a malicious extension on an admin's endpoint; or Login History shows logins to admin profile from an unfamiliar IP / device fingerprint while the legitimate user was also logged in elsewhere.

Detection signals

  • EDR/MDM: extension on a CVE list, or extension installed from outside the allowlist
  • LoginEvent: parallel sessions from divergent geolocations within minutes
  • Threat Detection: session-hijacking event fires

Containment (target: 15 minutes)

  1. Force-end all sessions for the affected user.
  2. Force password reset.
  3. Revoke all OAuth tokens issued to the user.
  4. Have the user remove the malicious extension; ideally reimage the endpoint.
  5. Re-enroll MFA with FIDO2.

Identify

Browser extensions inherit the user's session; actions taken via the extension look identical to actions taken by the user. Audit the user's recent activity from EVERY angle: Setup Audit Trail (config changes), Field History (data changes), ApiEvent (programmatic actions), ReportEvent (exports). Assume everything in the affected window may have been the attacker.

Notify

Internal stakeholders immediately; customers if their data may have been viewed or modified.

A.5 Scenario E — AI agent silent compromise

Trigger: The AI-agent-compromise indicators in Pillar 8.6 fire (output-hash drift on deterministic re-run, eval-bypass gap, provider-divergence event, or service-account use outside the expected job context).

Detection signals (any TWO concurrent => treat as Suspected AI Agent Compromise)

  • Output-hash mismatch on deterministic re-run for a Trust-Layer-bound agent
  • Eval result gap (decision_log entries with no corresponding eval result > 10 minutes after creation)
  • Provider-divergence event between primary and secondary AI provider on the same prompt
  • AI service account active outside its expected runtime context (cron / Cloud Run job window)
  • Concierge / agent recommendation rate deviates ≥ 15% from rolling baseline

Containment (target: 15 minutes)

  1. Set the agent's kill-switch flag (e.g., AGENT_ENABLED = false in custom metadata, or feature-flag service equivalent). The agent should fall back to deterministic / human-only path.
  2. Suspend the agent's service account at the cloud-provider IAM level.
  3. Halt any downstream processes that consume agent outputs (e.g., a workflow that auto-applies the agent's recommendation).
  4. Do not rotate session secrets immediately — preserve in-flight context for forensics.

Identify

  • Pull the trust-boundary log for the affected agent for the prior 48 hours; verify HMAC integrity
  • Diff agent decision-log output distributions against the prior 7-day baseline
  • Identify the injection vector: user-supplied form input, MCP-style context, or provider-side

Eradicate

  • If user-injection: add the pattern to the prompt-injection rule library; redeploy
  • If provider-side: failover to the secondary provider; open an incident ticket with the primary
  • If service-account credential exfil: rotate the credential; audit account permissions
  • Rebuild the affected agent runtime from the last known-good image

Notify

If the agent made user-facing recommendations during the compromise window, an in-app notification is generally appropriate ("We recently identified and resolved an issue with [Agent]; recently-generated recommendations should be reviewed"). Coordinate with legal counsel for any potentially material decisions affected.

For all five scenarios: file a post-mortem within 7 days (root cause, detection latency from first signal, response time to containment, lessons applied to the runbook). Update the runbook itself with anything you learned.

// File: AcmeSamlJitHandler.cls
// Pillar 1.6 — map IdP groups to Permission Set Groups on every login
public class AcmeSamlJitHandler implements Auth.SamlJitHandler {

    public User createUser(Id samlSsoProviderId, Id communityId, Id portalId,
                           String federationIdentifier, Map<String, String> attributes,
                           String assertion) {
        User u = new User();
        u.FederationIdentifier = federationIdentifier;
        u.Email = attributes.get('email');
        u.FirstName = attributes.get('firstname');
        u.LastName = attributes.get('lastname');
        u.Username = federationIdentifier + '@acme.com';
        u.Alias = federationIdentifier.left(8);
        u.LocaleSidKey = 'en_US';
        u.LanguageLocaleKey = 'en_US';
        u.EmailEncodingKey = 'UTF-8';
        u.TimeZoneSidKey = 'America/Denver';
        u.ProfileId = [SELECT Id FROM Profile WHERE Name = 'Standard User' LIMIT 1].Id;
        insert u;
        applyGroupBasedPSGs(u.Id, attributes.get('groups'));
        return u;
    }

    public void updateUser(Id userId, Id samlSsoProviderId, Id communityId, Id portalId,
                           String federationIdentifier, Map<String, String> attributes,
                           String assertion) {
        // Re-run group-based PSG application on every login — revoke + grant as needed
        applyGroupBasedPSGs(userId, attributes.get('groups'));
    }

    private void applyGroupBasedPSGs(Id userId, String groupClaim) {
        if (String.isBlank(groupClaim)) return;
        Set<String> idpGroups = new Set<String>(groupClaim.split(','));

        // Mapping in Custom Metadata: IdP_Group_Permission_Mapping__mdt
        // (DeveloperName = idp group, PermissionSetGroup__c = SF PSG developer name)
        Map<String, String> mapping = new Map<String, String>();
        for (IdP_Group_Permission_Mapping__mdt m : [
            SELECT DeveloperName, PermissionSetGroup__c
            FROM IdP_Group_Permission_Mapping__mdt
            WHERE Active__c = true
        ]) { mapping.put(m.DeveloperName, m.PermissionSetGroup__c); }

        // Determine target PSG set
        Set<String> targetPSGs = new Set<String>();
        for (String g : idpGroups) {
            if (mapping.containsKey(g)) targetPSGs.add(mapping.get(g));
        }

        // Revoke existing PSG assignments not in target
        Map<Id, PermissionSetAssignment> existing = new Map<Id, PermissionSetAssignment>([
            SELECT Id, PermissionSetGroupId, PermissionSetGroup.DeveloperName
            FROM PermissionSetAssignment
            WHERE AssigneeId = :userId AND PermissionSetGroupId != null WITH USER_MODE
        ]);
        for (PermissionSetAssignment psa : existing.values()) {
            if (!targetPSGs.contains(psa.PermissionSetGroup.DeveloperName)) {
                delete psa;
            } else {
                targetPSGs.remove(psa.PermissionSetGroup.DeveloperName);
            }
        }
        // Grant any remaining (newly authorized) PSGs
        Map<String, Id> psgIds = new Map<String, Id>();
        for (PermissionSetGroup psg : [
            SELECT Id, DeveloperName FROM PermissionSetGroup
            WHERE DeveloperName IN :targetPSGs WITH USER_MODE
        ]) { psgIds.put(psg.DeveloperName, psg.Id); }
        List<PermissionSetAssignment> toInsert = new List<PermissionSetAssignment>();
        for (String dev : targetPSGs) {
            if (psgIds.containsKey(dev)) {
                toInsert.add(new PermissionSetAssignment(
                    AssigneeId = userId,
                    PermissionSetGroupId = psgIds.get(dev)));
            }
        }
        if (!toInsert.isEmpty()) insert toInsert;
    }
}

            WHERE UsersId = :UserInfo.getUserId() AND IsCurrent = false
            WITH USER_MODE ORDER BY LastModifiedDate ASC];
        if (active.size() >= maxConcurrent) {
            // Revoke oldest sessions until under the limit
            for (Integer i = 0; i < (active.size() - maxConcurrent + 1); i++) {
                delete active[i]; // remove the AuthSession record (with sharing required)
            }
        }
        return Auth.SessionManagement.finishLoginFlow();
    }

C.3 Dynamic SOQL with typed binds

The example below is hardened against injection, but the LIKE '%term%' leading-wildcard pattern is index-defeating: at LDV scale (Account / Contact / Case > ~1M rows) it forces a full table scan and will eventually time out. For tokenized text lookup at LDV scale, refactor to SOSL with bounded RETURNING — see the LDV Cheatsheet §10 (index-defeating patterns) and §14 (SOSL refactor). 

public List<SObject> safeDynamicSearch(String objectName, String filterField, String userInput) {
    // Whitelist object and field names (never accept these from user input)
    // Per-object allowlist of safe fields (Case has no standard Name field; use CaseNumber/Subject)
    Map<String, Set<String>> allowedFieldsByObject = new Map<String, Set<String>>{
        'Contact' => new Set<String>{'Name','Email'},
        'Account' => new Set<String>{'Name','Industry'},
        'Case'    => new Set<String>{'CaseNumber','Subject'}
    };
    Set<String> allowedObjects = allowedFieldsByObject.keySet();
    Set<String> allowedFields  = allowedFieldsByObject.get(objectName);
    if (!allowedObjects.contains(objectName) || allowedFields == null || !allowedFields.contains(filterField)) {
        throw new AuraHandledException('Invalid query target');
    }
    // Pick a safe SELECT field per object (Case lacks Name; use CaseNumber)
    String selectField = (objectName == 'Case') ? 'CaseNumber' : 'Name';
    // Use AccessLevel.USER_MODE on queryWithBinds; do NOT also add WITH USER_MODE in the SOQL string
    String soql = 'SELECT Id, ' + selectField + ' FROM ' + objectName +
                  ' WHERE ' + filterField + ' LIKE :pattern LIMIT 20';
    Map<String, Object> binds = new Map<String, Object>{ 'pattern' => '%' + userInput + '%' };
    return Database.queryWithBinds(soql, binds, AccessLevel.USER_MODE);
}

I.2 Sample SOQL queries

Selectivity note. Lead each query with a bounded date range on the indexed EventDate field (not DAY_ONLY(CreatedDate) — wrapping a field in a function disables the index). Avoid NOT IN and != filters; SOQL treats them as non-selective and the optimizer can refuse them on large stores. Where you need a negative set, invert to a positive IN list, or fetch the candidate set and diff in client/Apex code. For the full set of selectivity / index-defeating rules, see the LDV Cheatsheet §09 (selectivity ladders) and §10 (index-defeating patterns); Salesforce primary source: Query & Search Optimization. 

-- All Bulk API exports > 5K rows in the last 7 days
-- Selective: bounded date range on indexed EventDate, then numeric filter.
SELECT EventDate, Username, RowsProcessed, OperationType, SourceIp
FROM BulkApiResultEvent
WHERE EventDate = LAST_N_DAYS:7 AND RowsProcessed > 5000
ORDER BY EventDate DESC
LIMIT 200

-- Report exports during off-hours (last 7 days)
-- Lead with EventDate range (selective), then Operation, then a positive
-- HOUR_IN_DAY IN (...) list. Do NOT use NOT IN -- non-selective.
SELECT EventDate, Username, ReportName, RowsProcessed, SourceIp
FROM ReportEvent
WHERE EventDate = LAST_N_DAYS:7
  AND Operation = 'Export'
  AND HOUR_IN_DAY(EventDate) IN (0,1,2,3,4,5,6,7,18,19,20,21,22,23)
ORDER BY EventDate DESC
LIMIT 200

-- Logins from new geos in last 24h
-- Anti-pattern alert: the original "NOT IN (subquery)" form is non-selective
-- and the optimizer will reject it on large LoginEvent stores. Instead, run
-- two selective queries and diff the LoginGeoId sets in client/Apex code:
--   (1) Geo IDs seen in the last 24h (today)
--   (2) Geo IDs seen across last 30 days with COUNT(Id) > 5 (baseline)
-- New geos = setDifference(today, baseline). Both queries are individually
-- selective on the indexed EventDate range.
SELECT EventDate, Username, SourceIp, LoginGeoId, Status
FROM LoginEvent
WHERE EventDate = LAST_N_DAYS:1
ORDER BY EventDate DESC
LIMIT 1000

SELECT LoginGeoId, COUNT(Id) cnt
FROM LoginEvent
WHERE EventDate = LAST_N_DAYS:30
GROUP BY LoginGeoId
HAVING COUNT(Id) > 5

O.4 Practical clock-management checklist

  1. Stop the clock from racing you. Once "discovery" or "awareness" is documented, the clock is running. Document the timestamp precisely.
  2. Engage counsel within hours, not days. Most jurisdictions' deadlines are too tight to defer legal review until the technical investigation finishes.
  3. Do parallel paths. Forensics, customer-facing notification drafting, regulator-facing notification drafting, and the post-mortem can all run in parallel; serializing them blows your deadlines.
  4. Pre-stage the templates. The first draft of "what we say to a customer" is faster to edit than to compose under pressure. Keep your templates in version control alongside the runbooks (Appendix A).
  5. Track the multi-jurisdiction matrix. A breach affecting EU + UK + US residents has at least three independent statutory clocks. Build a per-incident tracker that lists each jurisdiction, its deadline, and the assigned owner.
  6. Document the materiality call. For SEC 8-K, the 4-business-day clock starts on "materiality determination," not "incident discovery." Document the determination process and timestamp; this is itself a defensible artifact.

Appendix S · Industry-Specific Overlays

The ten pillars are general-purpose Salesforce CRM hardening; each industry vertical adds its own threat model, regulatory frame, and architectural specialization. This appendix sketches the deltas.

5.1 Financial Services Cloud (FSC)

  • Compliance overlay: Gramm-Leach-Bliley Act (GLBA) Safeguards Rule, New York Department of Financial Services (NYDFS) Part 500, Federal Financial Institutions Examination Council (FFIEC), sectoral state regulators. Appendix N's SOC 2 / PCI / GLBA mappings apply directly.
  • FSC-specific data sensitivity: the FinancialAccount, Securities Holdings, and Card objects carry by-default-sensitive data. Treat as Restricted classification (Pillar 7.1).
  • Connected Apps: custodian-bank integrations, depository-clearance integrations, Know-Your-Customer / Anti-Money-Laundering (KYC/AML) vendor integrations are per-user-named-principal candidates (Pillar 5.4).
  • Mutual TLS: generally required for Federal Reserve wire transfer (FedWire), SWIFT (Society for Worldwide Interbank Financial Telecommunication), and Automated Clearing House (ACH) gateways. Pillar 5.2 + 2026 cert transitions are operationally critical.
  • Common breach motif: wire-transfer fraud via business email compromise (BEC) feeding back into a Salesforce-tracked deal flow; gate large-dollar workflows with Transaction Security policies (Pillar 8.5).

5.2 Health Cloud

  • Compliance overlay: Health Insurance Portability and Accountability Act (HIPAA) Privacy + Security + Breach Notification Rules, state HIE (health-information-exchange) statutes, 42 CFR Part 2 for substance-abuse records, and the HIPAA Right of Access (NOT covered by Privacy Center; bespoke Apex usually required).
  • Health Cloud-specific objects: HealthCloudGA__EhrEncounter__c, care plan, problem-list, medication objects carry PHI. Field Audit Trail mandatory; Shield Platform Encryption strongly recommended.
  • BAA-bound integrations: every Connected App and ISV touching PHI must be covered by a Business Associate Agreement. Pillar 4 procurement framing.
  • Patient portals (Experience Cloud): Pillar 3 hardening is non-negotiable; Krebs-pattern guest-profile exposure of PHI is an OCR fine in waiting.
  • Hyperforce + EEE (Pillar 7.7): increasingly relevant for HIPAA's "appropriate technical safeguards" standard, particularly around BYOK.

5.3 Public Sector / Government Cloud

  • Authorization overlay: FedRAMP (Moderate / High depending on workload), StateRAMP (state-government cloud authorization program), IL2 / IL4 / IL5 for DoD-aligned tenants. Salesforce Government Cloud Plus carries FedRAMP High; Salesforce Government Cloud carries FedRAMP Moderate.
  • Identity overlay: typically Personal Identity Verification (PIV) / Common Access Card (CAC) / Derived-PIV smart card auth via SAML; Pillar 1.5 SSO architecture extended with smart-card support; FIDO2 hardware key (YubiKey 5 FIPS) often acceptable as an alternative.
  • Data-residency overlay: Hyperforce region restricted to specific US regions for FedRAMP-bound workloads. Pillar 7.7.
  • Public-records / FOIA: retention policies often legally fixed and longer than commercial defaults. Pillar 7.8 + 7.9.
  • Common breach motif: Krebs-pattern Experience Cloud exposure of resident data (the Vermont incident is the canonical example); Pillar 3 hardening is the entire mitigation.

5.4 Industries Cloud (Vlocity / OmniStudio)

  • Architectural specialization: OmniScripts, FlexCards, Integration Procedures, DataRaptors. Each has a distinct security model that does not map 1:1 onto core Apex / LWC / Flow.
  • OmniScript / Integration Procedure security: these run via a managed-package Apex layer; understand who-runs-as semantics for each step. Treat as Pillar 6, with Vlocity-specific verification needed.
  • DataRaptors: read/write data without USER_MODE awareness; explicit FLS validation in the DataRaptor configuration is required. Audit every DataRaptor that touches sensitive objects.
  • FlexCards reachable from guest: same exposure pattern as Aura / LWC in Pillar 3. Audit every FlexCard granted to a guest profile.
  • Contract / claim / order data: typically Restricted classification; Field Audit Trail recommended.

5.5 B2B Commerce / B2C Commerce

  • Compliance overlay: PCI DSS v4.0 if cardholder data ever touches the org (it shouldn't — payment processors should tokenize at the page-load layer). Pillar 7.1 classification + Pillar 5.2 mTLS to payment gateways.
  • B2C storefront (Experience Cloud): the entire Pillar 3 applies. The customer-facing site IS a guest-user surface; product-catalog metadata is intentionally exposed but customer accounts and order history are not.
  • Cart / order objects: WebCart, CartItem, Order, OrderItem; treat as Confidential classification minimum.
  • Connected Apps: ERP / inventory / payment-gateway / fraud-screening integrations are dense in B2B/B2C. Pillar 4's quarterly attestation is operationally critical given the integration count.
  • Common breach motif: credential-stuffing into customer accounts (loyalty fraud, gift-card cashout). Threat Detection's credential-stuffing signal (Pillar 8.4) is one of the highest-value-per-cost detections in this vertical.

Each overlay above is a starting point. Industry-specific Salesforce architecture is a deep specialty; pair this hardening reference with the corresponding Salesforce Industry Implementation Guide for your vertical.
